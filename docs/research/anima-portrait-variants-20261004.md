# Animaによる立ち絵差分の調査と設計方針

記録日: 2026-10-04（日本時間）

Animaで表情・衣装の差分を作るための調査結果と、会話で整理した製品方針を記録する。標準は従来どおりAnimaによる立ち絵1枚とし、差分生成は任意機能として検討する。表情編集には既存の技術候補があるが、本アプリでの編集品質・速度・必要メモリは未検証である。

この文書は調査・設計メモであり、利用手順や実装完了報告ではない。今回の作業ではモデル取得、画像編集の実行、アプリへの機能追加を行っていない。既存のQwen実験については[Qwen Image 2.1 キャラクター画像テスト](../setup/qwen-image-edit.md)を参照する。

## 製品としての方針

- 基本構成ではAnimaで立ち絵を1枚生成する。Qwen-Imageの導入を必須にしない。
- 立ち絵差分は、ユーザーがキャラ設定で作成を選んだメインキャラを対象にする。表情差分を作成していないキャラは、通常の立ち絵で表示する。
- 表情差分の目的は表現を豊かにすること。作成済みの表情を使い切るために、物語へ特定の感情や出来事を強制しない。
- 衣装違いを作る操作には、その衣装で登場させたいという意図がある。衣装はキャラ設定・物語上の状態として扱う。例は、主人公に普段着と魔法少女衣装を用意し、変身後は魔法少女衣装で登場させる構成。
- 将来のQwenによるt2i対応も見据え、基本画像の生成モデルと、差分の生成方式・有効化を分ける。表情差分をQwen専用には固定しない。

イベントCGの自動挿入は別機能として扱う。完成後調整でのCG追加・表示範囲編集、台本のタイムラインUIは将来対応であり、この文書の対象には含めない。

## 表情の定義と生成量

初期の表情定義は12種類とする。すべての表情画像を最初から生成する必要はなく、生成量を次の累積段階で選ぶ方針である。これは演出上の分類であり、Animaが全種類を安定して描き分けられることを確認したものではない。

| 段階 | 保有する表情 | 通常を含む枚数 | 通常からの追加生成枚数 |
| --- | --- | ---: | ---: |
| なし | 通常 | 1 | 0 |
| 軽量 | 通常、微笑み、怒り、悲しみ | 4 | 3 |
| 標準 | 軽量に、驚き、困惑、不安、真剣を追加 | 8 | 7 |
| 全種類 | 標準に、笑顔、泣き、恐怖、照れを追加 | 12 | 11 |

機能自体の既定は「なし」。ユーザーが表情作成を有効にする際の初期選択は「軽量」を候補とし、衣装ごとの対象表情を調整できるようにする。段階を増やすときは不足画像だけを生成し、開始前に追加枚数を表示する。時間の見積もりは、採用方式の実測後に行う。

表情注釈は、画像の有無とは独立して意図した表情を保持する。未作成の表情は、表示時に同じ衣装内の近い表情へ代用し、適切な候補がなければ通常へ戻す。注釈自体を代用先へ書き換えない。近さ・感情の強さに基づく具体的な代用表は今後定義する。

TTS向け感情と表情の注釈を同じLLM処理で扱い、画像がなくても注釈を残す方向で検討する。既存分類の画像を後から追加するだけなら、台本や注釈を再生成せず適用できる設計を目指す。表情分類自体の追加では、過去の注釈を再評価するかを別途決める。

## 現在の実装との境界

本アプリのAnima生成処理は、[image_runner.py](../../scripts/m0/image_runner.py)の `generate` でテキストから画像を生成し、立ち絵ではisnet-animeによる背景除去を行っている。画像編集用の入力画像・マスク・変更強度を渡す経路は、現在のアプリには接続していない。

採用済みDiffusersの `AnimaAutoBlocks` には `text2image` と `img2img` がある。ライブラリに経路が存在することと、本アプリで生成品質を確認したことは分けて扱う。現在の固定構成は[Diffusers環境メモ](../setup/diffusers.md)、APIは[採用commitの公式ソース](https://github.com/huggingface/diffusers/blob/7263f3317f6b392d62f41e9d75ed9d7e21fc5a5c/src/diffusers/modular_pipelines/anima/modular_blocks_anima.py)を参照する。

## 画像編集の技術候補

以下は2026-10-04時点の公開情報を確認した結果であり、本環境での編集実験結果ではない。

| 方式 | 確認できた機能 | 本件での位置づけ |
| --- | --- | --- |
| Animaのimg2img | 元画像を初期状態として再描画し、`strength` で変更量を調整する | 最初の比較基準。単独では編集箇所や同一キャラの保持を保証しない |
| Anima ControlNet-LLLite inpainting-v2 | Anima-Base v1.0向けの画像＋マスクによる部分編集 | 顔のマスク編集、衣装の局所編集の候補 |
| Anima ControlNet-LLLite v3実験版 | 参照画像からの表情編集を対象に学習・評価した追加モデル | 表情差分に直接関係する候補。開発中の方式として比較する |
| LanPaint | Animaでのinpainting・outpainting用サンプルを公開 | 部分編集の別方式。追加反復の負荷と統合作業を評価してから扱う |

img2imgの対応は[Diffusers公式仕様](https://huggingface.co/docs/diffusers/main/en/api/pipelines/anima)で確認できる。画像をリストで渡せることだけを、複数キャラの参照を意味的に統合する編集機能の根拠にはしない。

LLLite inpainting-v2の作者は、色の変化を抑えるためマスク付きimg2imgとの併用を推奨している。追加重みは約65.8MBで、ComfyUI用の実験ノードと独立した推論コードがある。本アプリのDiffusersへそのまま組み込めるとは未確認である。[作者のモデル説明](https://huggingface.co/kohya-ss/Anima-LLLite)、[配布ファイル](https://huggingface.co/kohya-ss/Anima-LLLite/blob/main/anima-lllite-inpainting-v2.safetensors)

v3の作者PRはDraftかつexperimentalで、全身絵の小さな顔などの細部の一貫性を改善中としている。短い表情指示だけでなく、通常生成に近いプロンプトを推奨している。公開された表情編集の追加重みは約77.7MB。これらの容量は追加ファイルの大きさであり、Anima本体を含むVRAM・RAM要件や生成時間ではない。[開発PR](https://github.com/kohya-ss/sd-scripts/pull/2413)、[表情編集の配布重み](https://huggingface.co/kohya-ss/Anima-LLLite/blob/main/anima-lllite-exp-change-2-000007.safetensors)、[ComfyUI対応PR](https://github.com/kohya-ss/ComfyUI-Anima-LLLite/pull/10)

LanPaintの作者はAnima対応サンプルを公開している。一方、確認したDiffusers移植の対応一覧にはAnimaが記載されていないため、現行ランタイムへの容易な導入を前提にしない。[LanPaint](https://github.com/scraed/LanPaint)、[Diffusers移植](https://github.com/charrywhite/LanPaint-diffusers)

## マスクの自動作成

### 検出と領域分割

マスク作成はAnimaの生成とは独立した前処理にできる。次の公開実装を候補とするが、採用するモデルと精度は未確定である。

| 候補 | 得られる情報 | 注意点 |
| --- | --- | --- |
| dghs-imgutilsのアニメ顔検出 | 顔を囲む矩形と検出信頼度。nano・standardモデルを選択可能 | 髪や眼鏡を除外した画素単位のマスクではない |
| コミュニティ製AnimeSeg | 顔、髪、左右の目・眉、鼻、口、衣装、肌、アクセサリーなどの領域 | 今回の絵柄・全身絵での精度と負荷は未測定 |
| SAM 3 | テキストや点・矩形などを条件とする領域抽出 | アニメ衣装への精度は別途評価が必要。軽量構成への採用は未定 |

根拠: [アニメ顔検出の仕様](https://dghs-imgutils.deepghs.org/main/api_doc/detect/face.html)、[AnimeSegのクラス定義と実装](https://github.com/suzukimain/AnimeSeg)、[SAM 3公式](https://github.com/facebookresearch/sam3)。

既存の背景除去・透過情報は人物全体の範囲として補助に使えるが、顔・髪・服を区別する情報は持たない。

### 表情編集のマスク案

以下は実装候補であり、まだ自動処理を実装・評価していない。

1. 採用済みの立ち絵から顔を検出する。顔が見つからない、複数の候補を絞れないなどの場合は、確認対象として扱う。
2. 眉・目・口を含む編集範囲を作り、前髪・眼鏡・顔に重なる手などの保護範囲を調整する。顔検出の矩形をそのまま確定マスクにはしない。
3. 必要な余白を付けて顔周辺を切り出し、編集に必要な解像度へ拡大する。座標変換とマスク境界の設定を保存する。
4. 編集結果を元の位置へ戻す。編集範囲外は元画像の画素を使い、境界をなじませる。輪郭を変えない表情編集では、元の透過情報も保持する。
5. 同じ元画像・同じ編集条件に対しては、マスクを再利用する。顔の向き、髪型、ポーズ、基準画像が変わった場合は再解析する。

各表情は、その衣装の採用済み基準立ち絵から生成する。笑顔を怒りへ、その結果を悲しみへ、と編集を連鎖させる方法は、元の顔から変化が蓄積する可能性があるため比較条件を分ける。

保存した編集範囲外の画素を保持できても、編集した顔自体の同一性を保証するものではない。小さい顔、横顔、目を隠す前髪、眼鏡、手の重なりは品質評価の対象に含める。

### 衣装編集のマスク案

既存の服の領域は、着せ替えの編集範囲を作る材料になる。ただし、新しい衣装が占める範囲まで考慮する必要がある。

普段着から魔法少女衣装へ変える場合、袖・スカート・リボンが元の服の外側へ広がることがある。変更後の形に応じて、周囲の肌や背景・透明部分にも編集を許可する一方、残したい顔・髪・手などを保護する。肌の露出量が変わる場合も、旧衣装の境界だけでは十分でない。

衣装で人物の輪郭が変わる場合は、元のアルファをそのまま使うと追加部分を切り落としてしまう。新しい衣装を含む透過マスクの再作成と、元画像との合成方法を別途検討する。背景除去の誤りも評価対象とする。

このため、まず表情用マスクの自動化を検証し、衣装用マスクは変更内容に応じた自動提案と確認を検討する。確認UIの具体形は未確定であり、完成後のタイムライン編集とは別の課題である。

## 負荷と保存方法の設計案

- マスクは元画像ごとに一度作って保存し、差分ごとの検出のやり直しを避ける。元画像のハッシュと、検出・分割モデルの版、範囲調整の設定を対応させる。
- GPUを使う領域分割と画像生成は順に処理し、必要がなくなったモデルを解放する。追加モデルを常駐させる前提にしない。
- 手直しはマスクの拡大・縮小や範囲修正を候補とする。自動検出に失敗した場合、無条件に全身を編集する代替処理は行わない設計を検討する。
- 生成方式、元画像・衣装の識別子、要求表情、マスク、切り出し座標、プロンプト、Seed、モデル版を記録する。元画像と採用済み差分を上書きせず、比較できる形で保存する。
- 表情の識別子と画像の対応を分けて持つ。将来の表情追加や生成方式の変更で、台本の意図した表情が失われない設計にする。

顔検出の導入や小さな追加重みだけで、処理全体が軽くなるとは断定できない。Anima本体、領域分割、編集方式の追加計算、読み込み・解放を含めて測定する。

## 次に行う小規模比較の案

実装採用を決める前に、同じ立ち絵を使って次を比較する。ここに記載する試験は未実施である。

| 試験 | 確認する内容 |
| --- | --- |
| 基本の表情 | 微笑み・怒り・悲しみから開始し、要求した表情と元キャラの特徴を両立できるか |
| 編集方式 | img2img、顔マスク＋LLLite inpainting-v2、表情編集v3の品質と負荷の差 |
| マスクの影響 | 自動マスクと手で修正したマスクを比較し、検出の誤りと生成側の問題を分ける |
| 難しい立ち絵 | 小さい顔、横顔、眼鏡、前髪・手の重なりへの対応 |
| 再現性と失敗率 | 複数Seedの結果を残し、良い一枚だけで判断しない |
| 別衣装 | 同じポーズの小さな衣装変更と、魔法少女衣装のような輪郭変更を分けて評価 |

顔・目・髪・体格・衣装・画風・透過輪郭の保持、マスク境界の違和感、要求表情の伝わり方を目視評価する。合成方式では編集範囲外の画素保持も確認する。ロード時間、推論時間、マスク作成時間、GPUの使用・確保ピーク、プロセスRAMピークを別々に記録する。

現時点では、Anima編集の最低VRAM・RAM、12表情すべての成功率、衣装変更の安定性を確定しない。大きなポーズ変更と複数キャラを参照した別構図CGは、表情差分とは別の検証課題として残す。
