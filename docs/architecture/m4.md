# M4：章継続・制作制御・公開版の境界

M3の承認固定・永続ジョブ・検査後公開を章単位へ拡張する。APIの `/api/m3` プレフィックスと既存のジョブ種別を保持し、生成処理・成果物・プレイヤーの互換性を維持する。

## 永続化

`006_m4_chapters.sql` で `m3_production` に次の管理項目を追加する。第1章の制作IDが物語系列のrootとなり、後続章は同じ承認スナップショットと `storyline_id` を参照する。

| 項目 | 内容 |
|---|---|
| `storyline_id` | 第1章の制作ID。章をまたぐ生成・停止・公開の系列を識別する。 |
| `chapter_number` | 承認した範囲内の章番号。同一承認版・章番号の制作は一件。 |
| `previous_narrative_artifact_id` | 生成入力として固定した前章の採用本文成果物。 |
| `previous_state_hash` | 前章の終了状態、または旧M3本文から抽出した開始状態のSHA256。 |
| `control_state` | rootの `running` / `stopping` / `paused` / `interrupted`。 |
| `m4_enabled` | 継続生成の有効化。新規制作は1、移行した旧M3は0。 |

既存の制作・成果物・build IDは移行で変更しない。`chapter_build` は章番号1〜100を許可し、公開済みレコードのUPDATE禁止を維持する。マイグレーションはトランザクション内で実行し、テーブルの再構築後に外部キーの整合性を検査する。

履歴スナップショットは各章の本文・ジョブ状態・素材要求・buildを参照として保持する。過去の履歴へ戻した場合は制作を凍結し、その時点に存在しなかった後続章を制作画面へ混ぜない。後から進んだ制作状態との競合があれば再開を拒否する。

## 物語状態と検査

`NarrativeResult` に `start_state`、`end_state`、`continuity_review` と系列・前章の参照を保持する。本文は従来どおりプレーンテキストを保存し、発話IDと原文位置の対応付けをアプリ側で検査する。

`StoryState` は人物の現在地、関係性、所持品、負傷、約束、内面感情と、人物ごとの知識を保持する。事実は固定の `fact_id` と説明で表し、人物の `knowledge` に取得章と根拠の発話IDを記録する。承認設定から開始前に知る情報だけを取得章0として扱う。新しい知識の過去への追加、既知情報の消失、未知の事実・発話への参照は拒否する。

伏線は固定された `StoryOutline.foreshadowing` の配列indexで追跡する。状態は `pending` → `planted` → `resolved` とし、指定された設置章・回収章、変化が起きた章、本文中の根拠IDを検査する。進展していない項目は以前の根拠を保持する。

第1章では承認資料から開始状態を構造化生成する。次章では前章の全体プロット・サブキャラ・終了状態をそのまま使い、人物ごとの知識と当章の役割をシーン設計・本文・レビューに渡す。章末に採用候補本文から終了状態を抽出し、全人物・全伏線を対象に内容レビューを行う。レビューは知識の取得前にその情報を話す・利用すること、場にいない人物への知識の漏洩、状態や伏線の根拠不足を検査する。

章境界の会話・動作をつなぐため、直前章末尾の発話・地の文を最大8行・合計5,000文字まで、原文の行を切断せず引用する。直前章の場所定義も渡し、同じ場所・時間帯・光・構図ならIDと画像プロンプトを含む定義全体を保持する。条件が変わる場合は別IDを使い、共通背景要求の一致と場面差分を区別する。

構造検査には `validate_narrative(result, snapshot, previous_narrative, require_state=True)` を使う。前章と当章の番号、プロット、サブキャラ、状態の完全一致を検査したうえで、サーバーがジョブに固定した系列ID・前章成果物ID・状態ハッシュを照合する。内容判断にはLLMの限界があり、根拠IDの存在検査だけで発話の意味を証明するものではない。

状態ハッシュは `StoryState.model_dump(mode="json")` を `ensure_ascii=False`、`sort_keys=True`、`separators=(",", ":")` でJSON化したUTF-8バイト列のSHA256とする。辞書キー順に依存せず、配列順と内容は保持する。

状態抽出・章全体レビューには、全文の発話ID・話者・表示本文を順序どおり渡す。音声本文が表示本文と異なる場合だけ別途含め、同一の場合の重複、原文offset、生成済み音声・感情注釈は入力から除く。これらは元の成果物には保持する。本文をLLMで要約したり、古い知識・根拠・伏線を切り捨てたりはしない。プロットと開始状態も同じリクエスト内で重複送信しない。

旧M3の推定開始状態は、前章全文だけを対象に全人物・全伏線の独立したレビューを行う。当章の検査はその状態と当章全文を照合し、二章分の本文を同じ入力に詰め込まない。前章レビューの結果・成果物ID・状態hashはtraceに保存する。推定状態が不採用になった場合は、その状態抽出から再試行する。

新しい推論リクエストは、稼働モデルの `/apply-template` と `/tokenize` でschemaを含む実プロンプトのトークン数を計測する。入力＋設定された出力上限＋128トークンの余裕がコンテキスト以内の場合だけ推論する。超過時は工程名と内訳を記録して停止し、本文を黙って削らず、回答枠やコンテキスト設定も自動変更しない。既存の完全一致応答キャッシュには新たな推論・計測を行わない。

## 旧M3との互換

状態を持たない旧M3の第1章は従来どおり読み込める。移行時に継続生成を有効化しないため、完成済み作品は画面閲覧・再起動だけで後続ジョブを追加しない。`start` または `resume` の明示操作で有効化する。

旧M3から第2章を作る場合は、そのジョブ内で前章の採用本文から状態だけを抽出する。結果には `predecessor_state_inferred=true` と `start_state` を保存し、抽出状態のハッシュを当章の `previous_state_hash` に固定する。前章成果物は変更しない。前章が既に `end_state` を持つ場合は推定を許可せず、同一の状態とハッシュを要求する。

M3の既存ジョブはプロンプトv4と従来の `llm/` キャッシュを使用する。`m4:true` の新規ジョブと後続章はv6の `llm-v6/` を使う。移行前の `llm-v5/` はリクエスト番号・seed・リクエスト全体のfingerprintが完全一致した応答だけ読み取り再利用し、旧ファイルを変更しない。これにより本文作成後に入力超過したジョブも、成功済みの本文・注釈を保持して新しい検査へ進める。ジョブ単位の入力フィンガープリント、固定した生成設定、LLM応答、完成結果ZIPは再取得・再起動後も再利用する。

## 生成順序と素材の再利用

前章の本文が検査・採用されると次章の `m3_narrative` を一度だけ登録する。画像・音声の完成は次章本文の登録条件にしない。入力には前章の採用本文・状態・成果物IDを固定し、元の生成ジョブへの依存を保存する。

ジョブ優先度は `101 - chapter_number` とし、先行章の登録済み工程を優先する。後続章のサブキャラ画像・基準音声・背景要求が先行章と同一の種類・対象ID・descriptorなら、先行章の生成を待って同じ成果物を参照する。台詞音声は発話ごとのジョブを保持する。

章の全素材が揃っても、前章の公開buildが無ければ公開を待つ。組み立て時にも前章の公開本文成果物が入力の前章と一致することを確認する。採用済み本文・素材から脚本とmanifestを組み立て、整合性を検査して新しい不変のbuildを登録する。生成結果の採用と後続処理の間で停止した場合は、制作状態の再取得や再開時の `advance` で不足する登録・組み立てを補う。

## 通常停止と即時中断

通常停止ではrootを `stopping` にし、新規claimと次工程の追加を抑止する。実行中のリースは有効なので結果を採用できる。実行中ジョブがなくなると `paused` になる。

即時中断ではrootを `interrupted` にし、実行中の `job_attempt` を `expired`、`error_kind=interrupted` とする。対象ジョブは同じIDの `pending` に戻し、利用者の中断で自動再試行枠を消費しないよう上限を調整する。失効したリースによるheartbeat・完了要求は拒否する。

ワーカーはheartbeatが409を返したときに試行専用の `CancellationToken` を取消す。取消しの通知は、その試行で所有する子プロセスの終了、GPUロック待ち、LLM呼び出し境界、音声セッション、成果物保存・返却の境界に伝わる。終了対象はワーカーが起動・所有したプロセスに限定する。通信エラーだけではリース失効と断定せず、期限切れによる復旧に委ねる。

`GenerationCancelled` は本文の形式・内容不合格と区別し、完了済みの応答キャッシュを失敗として無効化しない。再開はrootを `running` に戻して未完了ジョブを処理する。既に `failed` になったジョブは個別の再試行操作で戻す。

## 公開版・次章待機・セーブ

公開buildの検査記録と `chapter-manifest.json` に、当章本文、前章本文、前章状態ハッシュ、終了状態ハッシュを保持する。後章では前章の脚本成果物IDも記録する。

`GET /api/m3/builds/{build_id}/next` は指定buildの本文系列と状態ハッシュに接続できる公開章だけを返す。新しい版番号だけを理由に接続先を選ばない。旧buildに明示的な系列記録がない場合は、公開ZIP内の `narrative.json` と保存済み本文成果物を照合する。レスポンスは `waiting` / `ready` / `complete` と番号・ID・URLに限り、未読本文・題名・プロットを含めない。

ライブプレイヤーは章末でオート送りを止めて現在位置を保存し、5秒間隔で次章公開を確認する。利用者が「次の章へ」を押すと接続を再確認してbuild URLを開く。閲覧中に現在のbuildを差し替える処理はない。

保存データには `project_id`、`storyline_id`、`production_id`、`build_id`、`event_id` を記録する。復元時に版の一致、シナリオ名、イベント位置を照合する。章末は `chapter_end` として保持し、未完成次章や通信障害でも位置を失わない。静的配置では公開確認APIを呼ばず、書き出し範囲の終端を表示する。

## 書き出しとAPI

章単位のZIPは既存artifact URLから取得する。`GET /api/m3/builds/{build_id}/export` は、起点buildから接続できる公開済みの連続した章を `chapter-NNN.zip` としてまとめ、`chapters.json` に順序・build ID・ZIPのSHA256・終端、`README.txt` に配置方法を保存する。静的な章間自動移動は実装していない。ティラノ本体は同梱しない。

| API | 内容 |
|---|---|
| `GET /api/m3/projects/{id}` | 系列全体と章別の進行、制作制御状態、公開URL。 |
| `POST /api/m3/projects/{id}/start` | 承認版で開始、または組み立てを再開。既存制作のM4有効化も行う。 |
| `POST /api/m3/projects/{id}/stop` | `{"mode":"graceful"}` または `{"mode":"immediate"}`。 |
| `POST /api/m3/projects/{id}/resume` | 保持した制作状態から明示的に再開。 |
| `POST /api/jobs/{id}/retry` | 対象の失敗ジョブを再試行。 |
| `GET /api/m3/builds/{build_id}/next` | 指定公開版に接続できる次章の状態。 |
| `GET /api/m3/builds/{build_id}/export` | 指定公開版を起点とする章別ZIPの集合。 |
| `GET /player/{build_id}/player-context.json` | 鑑賞中のbuildと物語系列、次章確認URL。 |

## テストと未検証事項

`tests/integration/test_m4.py` は模擬ワーカーによる三章の制作・先行閲覧・章の不変性・素材再利用・停止・中断・再起動・系列不整合の拒否を検証する。`tests/unit/test_m4_narrative.py` は状態・知識・伏線・旧M3移行と生成呼び出しを、`tests/unit/test_worker_cancellation.py` は試行の取消しを、`tests/unit/test_player_chapters.py` とWebの状態変換テストは章末・保存・表示制御を扱う。

2026-09-24の全体検証でPython718件、Web31件、TypeScript・Viteビルド、Ruffが成功した。固定データによる実Edge・ティラノ確認では、制作制御と鑑賞の独立、章末保存後の再読込・復元、後続完成時の先行build/ZIPの不変性、明示操作での第2章移動を確認した。記録は `tmp/m4-browser-qa/report.json` に保存する。

実作品の旧M3第1章から継続する第2章でも、16k超過を修正し状態抽出・前章検査・当章整合性検査を実モデルで通過した。状態抽出入力は18,421から9,294トークンへ減少し、当章レビューは10,062トークン。96発話を含む全シーンが修正前の検査済みキャッシュと完全一致し、既存第1章の成果物も不変であることを確認した。記録は `tmp/m4-context/report.json`。最終変更後の関連108テストとRuffも成功した。

複数章全体の物語品質評価は未実施。コンテキスト16,384・既定出力3,072トークンは維持しており、より長い本文や知識の蓄積には入力予算を見て追加分割が必要になる。用途別モデル・reasoning切替、本文の部分改稿に伴う後続の再生成、複数PCの最適配置は後続の範囲とする。
