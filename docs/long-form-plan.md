# 長尺化（可変章数と2段の計画）の実装計画

2026-10-19〜21 の実験（`docs/long-form-experiment-handoff-20261020.md` と、そこから参照する実験記録）で確かめた構成を、製品に反映する。新しい仕組みを足す作業ではなく、実験用スクリプトが製品のコードを差し替えて動かしていた部分を、製品のコードとして書き直す作業として扱う。指示文は、実験で確かめた文面をそのまま使う。

## 1. 決定事項

| 項目 | 決めたこと | 根拠 |
|---|---|---|
| 計画の流れ | キャスト計画 → 章数の判定 → 出来事の連鎖 → 章への配分 → 章ごとの肉付け → 章の場面計画 | `long-form-expand-20261020.md`、`chapter-count-judgment-20261020.md` |
| キャスト計画 | 指示文に章数を書かない（「全N章の物語で」を「物語で」にする） | 章数の判定に使ったキャストの作り方（`probe_variable_chapters.py` の `cast_instruction_without_count`） |
| 章数の判定 | 持続力・構造・個性で見立てる依頼（`probe_chapter_count.py` の `--prompt criteria`）、上限8話 | `chapter-count-judgment-20261020.md` |
| 出来事の連鎖 | 出来事は章数〜章数×3個（今の3章の3〜9個と同じ比） | `check_text_long.py` の `chapter_models` |
| 章への配分 | 出来事の切れ目での区切り方を、手順数のばらつきが小さい順に30通りコードが挙げ、モデルが選ぶ（今の `sized_allocation` の指示文）。出来事が章数と同じなら、配分はコードで確定 | `--balanced` |
| 肉付け | 1章ずつ、骨組みの手順の前後に手順を足す。1章最大6手順、骨組みの言い換え・前振りの禁止、前の章と同じ役回りの禁止 | `--expand --expansion-steps 6 --distinct-steps --fresh-roles` |
| 章の範囲 | 章の場面計画には、後の章の予定を題名・役割・到達点だけで渡す。第2章以降の場面計画の前に、前の章の台本で済んだ当章の手順を照合し、済みとして渡す（`chapter_scope_guard`、2026-10-22 追加） | `scope-guard-20261022.md`（10/17 の `cast-size-20261017.md` で作った実験用の設定） |
| 最終章の締め | 最終章の肉付けでは、骨組みの最後の手順の後ろに手順を足さない（回答の形式で縛る）。最終章の場面計画には「最終章です。最後の場面の終了状態を、当章の予定の最後の手順の結果にします。」を伝える | `--closing-step-last --closure-end`（①＋案1） |
| コンテキスト | 16,384 / 32,768 / 65,536 の3段階から選ぶ。1トークン単位の設定はやめる | `long-form-16k-20261021.md` の「コンテキストの段と推論」 |
| 推論 | 32k以上でだけ選べる。上限は推論なしと同じ | 同上 |
| 章数の見せ方 | 目安を示し、ユーザーが段の上限まで変えられる。既定値は「目安と段の上限の小さいほう」。目安が段の上限を超えるときだけ「4話以上を設定するにはコンテキスト長を32k以上にしてください」（赤字）を出す | ユーザーとの相談（2026-10-21） |
| 既存の作品 | 今の作品・計画は、保存した方式のまま動く | 製品の `script_options` の扱い（後述） |

### 段ごとの上限

| 段 | 章数 | メイン | キャラ上限（メイン込み） | 衣装違い（合計） | 推論 |
|---|---|---|---|---|---|
| 16k | 3まで | 3人まで | 4人 | 3着まで | なし |
| 32k | 8まで | 3人まで | 8人 | 制限なし（今の1人4着まで） | あり |
| 64k | 8まで | 3人まで | 11人 | 制限なし（今の1人4着まで） | あり |

- キャラ上限は、今の目安（`cast_limit_guide`、16k:5 / 24k:6 / 32k:8 / 64k:11、推論ありで1人減らす）を、この表の値と段に置き換える。目安ではなく上限にする（承認画面の入力の最大を段の値にする）。推論ありで1人減らす扱いはやめる（推論は回答の枠を使い、入力の量は変わらない）。
- メインは、どの段も今のまま3人まで。
- 16kの衣装違いは、メイン全員の別の姿の合計数で数える（1着あたり約85トークンで、誰が着るかで量はほとんど変わらない）。

## 2. STEP3へのサブキャラの移動（決定）と未決の設計

章数の判定はキャスト計画の後に行う。キャスト計画を今のSTEP4（承認後の計画の段）からSTEP3へ移し、サブキャラの確認・修正をSTEP3の別タブで、メインに近いUIで行う（2026-10-21 決定）。

| 段階 | 行うこと |
|---|---|
| STEP3・メインのタブ | 今と同じ（設定・関係性・立ち絵・基準音声） |
| STEP3・サブのタブ | キャラ上限を決めてキャスト計画を作る。サブの設定・関係・立ち絵・基準音声を、メインに近いUIで確認・修正する。サブを作った後と直した後に、章数の判定を行う |
| STEP3の承認 | 章数を選ぶ（目安・既定値・赤字の案内）。メインとサブを承認スナップショットに入れる |
| 承認後（STEP4の生成） | 承認したキャストから、出来事の連鎖 → 章への配分 → 肉付け。キャスト計画は作り直さない |
| STEP4 | 全体プロットの確認・修正 |

- 実験でも、章数の判定に使ったキャストのまま計画するのが正しい手順だった（`--cast-from`）。承認スナップショットにサブが入れば、製品でもそうなる。
- サブの立ち絵・基準音声は、メインと同じくSTEP3で作る（今はSTEP4で作っている）。
- STEP1・STEP2の章数の欄は、新しい作品では使わない。承認スナップショットの `world.chapterCount` は契約に残し、既存の作品が使う。

- STEP4から、サブキャラの確認・修正・追加・削除をなくす。
- ユーザーに見せる全体プロットは、肉付けした後の1つだけ。STEP4の確認・直接編集・AIの修正もそれに対して行う。骨組みは、どう作ったかの内部の記録として保存するだけで、画面には出さない。

### 暫定の形（STEP3のサブのタブができるまで）

STEP3のサブのタブは後で別に計画する。それまでは、STEP4を2段階にする。

| 段階 | 行うこと |
|---|---|
| STEP3の承認 | 今と同じ（メインの承認。キャラ上限の入力も今の承認画面のまま） |
| STEP4・1段目 | キャスト計画と章数の判定を作って止まる。サブキャラの確認・修正（今のSTEP4のサブ編集）と、章数の選択（目安・既定値・赤字の案内）を行う。サブを直したら、章数の判定をやり直す |
| STEP4・2段目 | 選んだ章数で、出来事の連鎖 → 章への配分 → 肉付けを作る。全体プロットの確認・修正だけを行い、サブキャラの編集は置かない |

サブが決まってから全体プロットを作るという点で、最終的な形と同じ。STEP3のサブのタブができたら、1段目をSTEP3へ移す。

## 3. 変更する箇所

### 3.1 生成（`services/worker/generation/`）

実験用スクリプトが差し替えていた箇所を、製品のコードにする。

- `script_plot.py`
  - 連鎖の `events`、`ChapterAllocation` / `StepChapterAllocation` の `chapters`（今は `min_length=3, max_length=3`）を、章数に合わせる。`check_text_long.py` の `chapter_models` と同じ範囲。
  - 連鎖と配分の指示文の「全3章」「3〜9個」「3章の各区間で」「均等に三分割」を、章数で書く（`use_chapter_count` の置き換えと同じ文面）。
  - `check_core` を、承認した章数で確かめる。
- `script_cast.py`
  - `cast_instruction` から章数を外す。「全3章では1〜2人を目安に」の文（`CAST_ANCHOR` など）の扱いを、新しい方式では使わない形にする。
  - `cast_limit_guide` を段ごとの上限に置き換える。
  - `ScriptOptions` に新しい方式の項目を足す（未設定なら保存形から消える、今の項目と同じ作り）。
- `script_continuation.py`
  - キャスト計画の3章限定（`count == 3` の分岐、`approved_chapter_count != 3` の確認）を、新しい方式では外す。
  - キャスト計画の後に、章数の判定の段を足す（`probe_chapter_count.py` の `CRITERIA_EXAMPLES` と `CRITERIA_TASK`、上限8）。回答の形式は実験と同じ JSON。
  - `outline` に、配分の区切り方の候補（`balanced_options`）と、肉付けの段（`use_expansion` の `outline`）を入れる。肉付けの指示文（`EXPANSION_INSTRUCTION` → `DISTINCT_EXPANSION_INSTRUCTION`、`FRESH_ROLES_RULE`、`FINAL_EXPANSION_RULE`）と、回答の形式（`ChapterExpansion`、`after_step` の最大、`added_steps` の最大）は実験のまま。骨組みと肉付け後のプロットの両方を保存する。

  - 章数を、承認スナップショットの `world.result.chapterCount` ではなく、選んだ章数（計画）から取る。STEP5の制作は、承認した計画の章数で進める。
- STEP4のAIの修正（`plan_content` を直す工程）が、3章以外のプロットと、肉付けした手順を扱えるようにする。

### 3.2 コーディネーター（`services/coordinator/`）

- `planning_service.py`: 新しい計画の `script_options` に新しい方式の項目を入れる。今の計画（項目なし）は、今の文面と上限のまま動く。新しい計画は、1段目（キャスト計画と章数の判定）で止め、サブの修正で判定をやり直し、選んだ章数で2段目を始める。2段目は、1段目で確定したキャストを作り直さずに使う。
- `llm_settings.py`、`packages/contracts/llm_settings.py`: コンテキストを3段階の値だけにする。16kでは推論を「なし」だけにする。
- `cast_limit_choice`: 段の上限を返す。承認時に、キャラ上限・衣装違いの合計が段の上限を超えていたら止める。
- `m3_service.py`: 制作の章数を、承認した計画から取る。

### 3.3 Web（`apps/web/src/`）

- `LLMSettings.tsx`: コンテキスト長を3段階の選択にする。16kでは推論を選べなくする。
- STEP4・1段目（`PlanningReviewPanel` など）: サブキャラの確認・修正（今のSTEP4のサブ編集を使う）と、章数の選択（目安、既定値、赤字の案内）。章数を選んで2段目へ進む操作。

- `WorldSteps.tsx`: 新しい作品では章数の欄を出さない。
- 「全N章」の表示を、選んだ章数から出す。

### 3.4 既存の作品の扱い

製品は、新しい計画にだけ `script_options` の項目を入れ、項目のない計画は作ったときの文面と上限のまま動かしている（`planning_service.py` の `planned_cast_appears` などのコメント）。長尺化も同じ作りにする。今の作品・計画・制作途中の章は、そのまま再開できること。`planning_protocol` の版を上げる要否は、実装時に確かめる。

## 4. 実装の順序と確認

1. **設定**: コンテキストの3段階、推論の可否、キャラ上限の段。単体テストと Web のテスト。
2. **章数に合わせた計画**: 連鎖・配分の章数の固定を外し、配分の区切り方の候補を入れる（肉付けなし）。3章の今の作品の計画が変わらないこと（今のテスト）。
3. **肉付けと締め**: 肉付けの段と、最終章の場面計画の一文。
4. **章数の判定とSTEP4の2段階（暫定）**: キャスト計画の後の判定、1段目で止める処理、サブの修正後の判定のやり直し、章数の選択、2段目への選んだ章数の受け渡し、STEP5の章数。
5. **画面の残り**: 衣装違いの上限、「全N章」の表示、STEP1・STEP2の章数の欄、2段目からサブキャラ編集を外す。
6. **実験との一致の確認**: 製品のコードで、実験と同じ入力・シード・条件の作品を書き、計画（キャスト計画・連鎖・配分・肉付け）が実験の出力と一字一句同じになることを確かめる。依頼の文面と回答の形式が同じなら、同じシードで同じ回答が返る（実験でも、同じシードの再実行で第1〜3章の肉付けまで一致した）。対象は `long-form-16k-20261021.md` のひだまり3章・16k（`outputs/long-form-20261021/hidamari-ud-3ch-16k`）。章数の判定は実験では別のスクリプトで行ったので、判定の段は `chapter-count-judgment-20261020.md` の結果と同じ話数になることを確かめる。

各段で、`tests/unit` と `tests/integration`、Web の型検査とテストを通す（コマンドは `docs/long-form-experiment-handoff.md` の「作業上の注意」）。

### 章の範囲（2026-10-22 追加）

新しい計画の `script_options` に `chapter_scope_guard` も入る。この実装（10/21）では入れていなかった。長尺化の実験は、そのときの製品の計画オプション（`planned_cast_appears`・`open_scene_cast`・`cast_limit`）で走らせていて、`chapter_scope_guard` は10/17 に実験用の設定として作ったまま、採否を決めていなかった。この計画は「実験用スクリプトが差し替えていた部分を移す」範囲で組んだので、対象に入らなかった。製品のひだまり4章で第3章が第4章を先取りして見つかり、本体のジョブから第3・4章（鉄と血は第5・6章）を有効にして書き直して確かめた（`scope-guard-20261022.md`）。`check_text_long.py --product` も同じく有効にする。10/22 より前に始めた長尺化の計画は、STEP4で承認（再承認）したときに承認の設定へ足し、その承認から始まる制作は第1章から有効になる（計画そのものはこの設定を使わないので、プロットは変わらない）。すでに始まっている制作は、章の引き継ぎがその設定で検査されるので、作ったときのまま動く。

### 実験との違い

- **3章も長尺化の流れになる。** 今日の3章・16kの実験（`long-form-16k-20261021.md`）は、`check_text_long.py` が3章のときに製品の3章の流れを使ったので、配分は区切り方の候補なし、キャスト計画は「全3章の物語で」だった。製品の `long_form` は、3章でも区切り方の候補を挙げる配分と、章数を書かないキャスト計画になる。4章以上の実験と同じ形。
- **章数の判定の依頼の形。** 実験（`probe_chapter_count.py`）は、独自のシステム文と、承認設定とキャストをJSONにした資料を渡し、回答の形式を縛らなかった。製品は、同じシステム文と依頼文に、他の計画の段と同じ形の設定を渡し、回答の形式をJSONスキーマで縛る。判定の結果が実験と同じになるかは確かめていない。
- **肉付け後のプロットの経路の表示。** 実験は肉付け後も各章の `route`（表示用の要約）を骨組みのまま残した。製品も同じだが、STEP4の計画の内容は、コーディネーターが受け取るときに出来事から `route` を作り直す。場面計画以降は `route` を読まず出来事を読むので、生成には影響しない。

### 実験と同じ依頼になっているかの確かめ方

`check_text_long.py --product` は、実験の差し替えを使わずに製品の `long_form` で台本まで書く。同じ入力・キャスト（`--cast-from`）・シードなら、依頼の通し番号も同じになり、依頼の文面が同じなら同じ回答が返る。コンビニ2章・16k（`--cast-from` で書いた実行）で確かめる:

```powershell
uv run python -X utf8 scripts/story/check_text_long.py `
  --input outputs/long-form-20261020/inputs/konbini-16k.json `
  --output-dir outputs/long-form-20261021/konbini-product `
  --chapters 2 --skip-staging --cast-from outputs/variable-chapters-20261019/konbini-open --product
uv run python -X utf8 scripts/story/compare_runs.py outputs/long-form-20261020/konbini-ud-2ch-16k-closure outputs/long-form-20261021/konbini-product
```
