# コンテキスト配分と章間接続の改善計画

作成日：2026-09-26。状態：prompt 12 / implementation 13 / contract revision 11として実装済み。[自動テストと保存済み資料の容量診断](experiments/script-continuation-r12-implementation-20260926.md)と、同じ承認設定での3章通し生成を完了。[通しレビュー](experiments/script-continuation-r12-review-20260926.md)を受けた次の変更は[決着の準備と会話の具体性を改善する計画](story-causality-and-dialogue-plan.md)を参照。本書の履歴保持・容量配分・章間接続の方針は維持する。運用設定は[作劇実験の手順](setup/story-debug.md)を参照。

[直接場面計画版のレビュー](experiments/script-continuation-r11-review-20260926.md)を受けた次の実装計画。[章の継続を優先する方針](chapter-continuation-reset-plan.md)を引き継ぎ、今回の容量不足と章間接続の欠落への具体策を定める。

## 目的と維持する条件

3章のビジュアルノベルが、前章で実際に起きたことを受けて進み、結末まで到達できるようにする。16kを24GB環境を意識した最適化の目標とし、32k・64kなど環境に応じた設定も使える構成を維持する。16kで全設定・全作品が必ず収まるとは約束しない。

- 比較設定は承認済み「境界線のエクリプス」、seed 1、全3章。設定を別作品に変えない。
- Gemma・reasoningなし・画像音声なしを維持。モデル本体とKVキャッシュの量子化変更は今回の比較に混ぜない。
- 人物ID付き台詞、NARRATOR、発話分離、演出、キャスト・場所・素材要求、Script/Tyrano出力を維持。
- 各章約10分、本文約4,000字・台詞約2,000字の補助目安を維持。文字数から再生時間を保証せず、短縮を成功条件にしない。
- M3型の直接ScenePlanを使う。行動番号の全件照合、意味採点、別モデルの常設検査、合格までの修復ループを追加しない。
- 既存作品・失敗記録は保存し、実装後の実験は別の出力先とprotocolで区別する。

## 現状の証拠

第1→2章は救出と協力約束から、律との対立、実際の記憶喪失、遥との衝突へ進んだ。一方で第3章計画は、現実へ戻った凪を、連れ去られた後の状態として扱った。第3章の救出動機を支える出来事がどの場面にも割り当てられていない。該当する帰還の原文と履歴メモは計画入力に存在していた。

容量は停止する前から不足していた。第2章の本文執筆では第1章原文の大半とメモが落ち、第3章第1場面の送信前には第2章末場面だけに絞っても16,647 tokensとなり、16,384を263超えた。

全場面に8,192 tokensの出力枠を予約した一方、今回8場面の実出力は736〜1,409 tokensだった。本文だけでなく話者ID・改行を含む値。実際の短い出力だけを根拠に上限を一律1,409へ下げることはしない。

執筆入力には、章内全場所の定義と当場面の場所の再掲、当場面に不在のメイン人物の詳細、全メイン人物間の関係、類似する継続指示が含まれている。第2章最終場面では設定欄だけで6,205文字、うち場所1,309文字・関係1,154文字・人物1,969文字だった。これは文字数でありトークン数とは区別する。当章のevents・route・conversation_topicsは既に執筆入力から除かれているので、同じ削減を再実装しない。

## 1. 入力と出力の容量を工程ごとに配分する

### 場面の出力枠

場面計画のlength_weightから算出する本文・台詞の目標量を、内部の数値データとして保存する。現状のようにobjectivesの日本語から数値を読み戻さず、表示用の文章と予算計算が同じ数値を参照する。公開ScenePlan・Script契約へ予算都合の変更を持ち込まず、内部の付随データで扱う。

執筆ごとの出力枠は、場面の目標量、台詞量、話者IDと改行の負荷、同モデルの保存済み実測から見積もる。典型的な短い場面では2,048〜4,096 tokensを初期候補とする。これは調整の出発点であり固定上限ではない。1場面で章全体を書く場合や分量設定を増やした場合は、必要に応じて既存の8,192枠以上も設定できるようにする。

実装時に固定する初期推定係数・安全余裕・下限・上限は設定とともに保存する。作品の途中で計測値に応じて推定を更新する場合も、使用した過去の実測と採用値を記録して再開時に再現する。入力に収めるために作品の目標字数や必要な回答枠を勝手に小さくしない。

選んだ同じmax_tokensを、送信前のコンテキスト計測と実際の生成要求へ渡す。出力枠とcontext_sizeは別の値として扱う。出力枠を小さくしただけでVRAMが同じ割合だけ減るとは報告しない。

既存の上限到達時の続筆を維持する。続筆では途中原稿・接続文字列・grammarも入力に入るため、その状態でも予算を測る。続筆回数を際限なく増やさず、途中原稿の保存と明確な停止を維持する。

章計画など他工程の出力枠は、まず実測を記録する。今回の主な修正は場面執筆であり、すべての工程を一律に縮めない。

### 工程別の資料

| 工程 | 保持する資料 | 整理する資料 |
| --- | --- | --- |
| 全体プロット | 承認設定、全体のキャストと関係、結末、作品規模 | 台詞・素材生成専用の詳細 |
| 章計画 | 実台本の現在地、必要な履歴、当章の目的と出来事、後続章の目的、選択可能なキャスト・場所 | 同じ出来事の重複要約、独立した過去扱いの開始予定 |
| 場面執筆 | 当場面の人物・場所・計画、同章で生成済みの本文、前章までの実績、後続場面の担当と止めどころ | 章内の全場所定義、当場面に関係しない人物・関係の詳細、同じ場所・終了状態の二重記載 |
| 発話分離・演出 | 対象台本の全文、対象場面と必要な人物・場所設定 | 作品全体の計画など対象処理に不要な説明 |

不在でも会話中で重要となる人物は、役割・関係・話者への影響を残す。当場面のcharacter_idsだけで機械的にすべてを消さない。人物の口調や価値観、作品の能力ルールなど執筆に必要な設定は保持する。完全な承認設定・素材情報は保存データに残し、工程向けの入力表示だけを絞る。

共通の継続方針は一箇所にまとめ、工程別指示で差分を補う。指示を削った量ではなく、実際に残った資料と生成内容で評価する。

## 2. 過去の本文と代替メモを両方落とさない

今回の3章PoCでは次の順序で容量を使う。

1. まず、整理後の設定・予定・原文全文で計測する。収まるなら原文を優先し、同じ内容の要約は重ねない。
2. 収まらなければ、遠い未来の詳細を章の目的・終点の短い表示へ切り替える。未来の資料を過去の実績へ混ぜない。
3. 古い完了章の原文を省く場合、その章の保存済み本文由来メモを必ず残す。原文の一部を残す場合も、除いた範囲を補うメモを残す。
4. 直前の完了章の末場面は原文で保持する。同章内ですでに生成した場面は、この3章PoCでは原文全文を保持し、場面計画を実績の代わりにしない。
5. これらと必要な出力枠が収まらない場合、必要資料と不足量を示す容量エラーにする。設定済みの拡張範囲があれば、その範囲で扱う。

同章内の場面ごとに新しい要約生成工程は追加しない。まず重複整理と出力枠の変更でどこまで原文が入るかを検証し、それでも不足する長い章への方式は実測を受けて判断する。

履歴メモは既存のhandoff工程を使う。「実際の結果と所在」「失われたもの・変わった関係」「継続中の約束・未決事項」を簡潔に残す。人物の推測はその人の発言として記録し、次章の展開案は入れない。毎回全項目を無理に増やす細かな台帳にはしない。

現在のメモ取得失敗時の「未記録」という文は、履歴を保持したことに数えない。その場合は原文を使う。原文も入らなければ資料不足として停止する。これは内容の意味採点ではなく、必要な過去資料を実際に送れるかの確認である。

## 3. 予定の開始条件を、過去の実績として再生成しない

### プロット作成

冒頭の承認設定を起点に、出来事の行動と結果を順につなぐ現在の短いプロット方式を保つ。ただし、後続出来事のstart_conditionを独立した自由文として生成させる構造はやめる。

最初の開始状態だけを承認設定から生成する。以降の表示用start_conditionは、前の出来事の最後のresultから組み立てる。それ以前の出来事も同じ連鎖として保持し、最後の一文だけを世界全体の状態とは扱わない。章配分時に新たな開始事情を作らない。移動・捕縛・発見・関係の変化などが後の目的に必要なら、それを起こす行動を出来事列の中に置く。既存の表示用routeが必要なら、同じ出来事の結果から投影する。

これにより独立した開始文だけに大事件が紛れ込む場所を減らす。隣接する文章の完全一致や意味の全件照合を、新しい合格条件にはしない。これだけで出来事の抜けを完全に防げるとは扱わない。

### 章計画と執筆

入力を「実際の出発点」と「これから目指すこと」に分ける。

- 実際の出発点は、保存済み台本と本文由来メモから渡す。章計画者がプロットを材料に過去を作り直す欄にはしない。
- プロットからは当章の目的・予定する行動・結末への役割を渡す。開始条件が実台本と異なる場合も、予定側の情報として扱う。
- 現在のcontinuation欄は、実績の新しい要約を兼ねず、実績を受けて当章で何を描くかという短い接続方針へ役割を限定する。執筆入力でも未来の予定の欄に置く。
- 必要な出来事がまだ起きていなければ、当章のrequired_eventsへその過程を置くか、実際の状態から同じ目的へ進める手段を選ぶ。未発生の大事件をscene.start_stateへ埋めて済ませない。

今回なら、帰還済みの凪が後に連れ去られる経緯を描くか、帰還後の実態に合った対立・救出の進め方を作る。これは検証用の例であり、人物名・捕縛・救出などをコードへ固定しない。移動、情報の入手、和解や決裂など別設定の接続にも同じ原則を使う。

ScenePlanの目的・開始状態・required_events・終了状態はそのまま直接作る。別の行動対応表、未来経路の置換表、未達一覧は復活させない。大きな逸脱時の作品全体の自動再プロットは今回の対象外とする。

## 4. 会話の中身を増やし、既知の内容の再演を減らす

当章の主筋を進める場面では、既に知った苦しみや協力の約束を繰り返す代わりに、その後の試行、新しい手がかり、相手の具体的な反応へ進める。これは「すべての場面で新事件を起こす」という条件ではない。

日常や軽い掛け合いの場面には、人物自身の用事・好み・遊び・気まずさなど、会話を続けたくなる具体的な接点を持たせる。サブキャラも主筋への不可欠性だけで選ばず、交流や生活感を担えるようにする。会話材料の項目数や上限を増やすより、既存項目の内容を具体化する。

第2章の凪のように、後半が悲鳴や呼びかけだけになる場合は、本人の試みや相手への働きかけを場面計画へ織り込む。ただし全員の均等な台詞数・成長・和解を要求しない。地の文は状況や内心に使い、説明の反復を減らして浮いた分量を会話と応答へ回す。

## 5. 16kから拡張できる運用と記録

16k・32k・64kなどの設定は、実行環境で許された上限・モデルの確認済み上限・稼働サーバーの実際の容量の範囲で解決する。新しい固定16k制限は作らない。量子化条件が同じでも各GPUで収まるかは別途実測する。

現行のallow_expansionは、許容最大サイズでサーバーを起動する方式であり、16k分のVRAMだけで開始して必要時に無償で増える仕組みではない。この挙動を隠さず、比較実験は16k固定の実行と、明示的に拡張した実行を区別する。VRAM不足に応じた自動量子化・自動モデル交換は追加しない。

保存済み実験のcontext設定だけを上書きして再開しない。まず同設定での再開を維持し、設定やprotocolを変える実験は新しい出力先に分ける。旧章を使う局所診断では入力元とハッシュを明記し、新方式による通し生成と混同しない。

要求ごとに入力の実測、出力予約、実出力、余白、実際のcontext、原文範囲、代替メモの出典・採用理由、除外した任意資料を保存する。分量の推定根拠と続筆回数も記録する。部品別の文字数をトークン数として報告せず、全要求の予算は実tokenizerで確認する。

通常UIや素材生成全体の改修には広げない。実装は独立した `script_continuation_v1` 実験経路に適用し、既存作品・旧実験は変更しない。

## 検証と完了の判断

### 実装時の確認

- 保存されたr11の実入力・実台本を使い、旧方式と変更後の要求を再構成してtokenizerで測る。場面執筆と第3章計画の両方を対象にし、収まったかだけでなく原文・メモが何を保持したか比較する。この計測では物語を再生成しない。
- 自動テストでは、本文と代替メモの両方が消えないこと、メモ取得失敗時の扱い、同章の既出原文の保持、入力と送信の回答枠一致、長い場面・設定拡張・続筆・再開の予算を確認する。
- 16k固定では勝手に拡張しないこと、上限内の32k・64k設定が解決されることを確認する。設定テストだけで実機VRAMや作品品質を検証したとは報告しない。
- 人物ID付き台本、発話・演出、キャストと背景の要求、Script/Tyrano出力を確認する。検査項目を物語の意味採点へ広げない。
- 小規模な実生成を行う場合は、保存済み第2章からの第3章計画で「未発生の出来事を実績化せず接続できるか」を診断する。これは旧プロットを使う接続だけの確認であり、変更したプロット方式全体の実験には数えない。

実装と自動・小規模確認の後、一度結果を報告する。新しい全体方式の評価は、その後の実行依頼を受け、同じ承認設定・seed 1でプロットから3章を生成して行う。容量・形式・その他の理由で停止したら、生成済み範囲と原因を報告し、その場でコード変更と再生成を重ねない。

### 通し生成後に人が読む観点

1. 第2・3章が、実際の前章結果から始まり、必要な移動・発見・拘束・関係変化などの経緯が読めるか。
2. 過去の約束や損失を継承し、同じ初対面・発見・協力約束を初めてのように再演していないか。
3. 原文やメモを保持した状態で3章まで生成できたか。単に履歴を捨てて16kへ収めたものは成功にしない。
4. 本文量を保ち、会話を通じた展開と人物らしい反応が増えたか。比率だけで合格にしない。
5. 第3章の決着が実際の積み重ねから成立しているか。

これらは生成後のレビュー項目。生成を止める常設LLM検査にはしない。16kで保持すべき資料がなお収まらない場合は、実測した必要容量と残る大きな入力を提示し、拡張や圧縮方式の次の判断材料にする。
