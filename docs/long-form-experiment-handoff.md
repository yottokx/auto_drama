## 長尺化を考えるきっかけ

鉄と血の叙事詩の再生成版（推論なし、上限8）が、オリジナル版（推論あり、旧い流れ）より薄く感じられた。数字は `docs/experiments/cast-size-20261017.md` の最後の節にある。要点:

- 再生成版は1章約4,000字の目安どおり。オリジナルは目安の1.5倍ほどで、長すぎた側。
- 薄さの主因は、プロットの出来事が少ないこと（第1・2章は出来事1つ・手順2つずつ、全体で手順8つ）。メイン3人＋サブ3人で分けるので1人あたりの見せ場が少なく、第2章は主人公が一度も出ない。
- 予定したサブ（リィン）が、プロットで手順を1つも持たずに通った（指示文だけで、コードの確認が無い）。
- 推論の有無も違うので、どこまでが推論の差かは切り分けていない。

ユーザーの考え（2026-10-19）:

- 現状は3章固定だが、当初は最初に目標章数を指定する予定で、UIにはその入力が残っている。
- LLMの裁量で章数を可変にするのも一つの手段。
- 懸念は3つ。後の章ほど計画時のコンテキストが増えること、長尺化しても整合性が取れるか、そして一番の問題は生成と内容レビューの時間が増えること。

## 章数についての今のコード

- STEP1の章数入力（`apps/web/src/WorldSteps.tsx`、1〜99）は `world.chapterCount` として保存され、承認スナップショットから `approved_chapter_count` として生成に渡る（`planning_run.CommonPlanRun`、`script_production`）。
- データベースの75作品はすべて3章。4章目以降を作った作品は無い。
- キャスト計画 → 出来事の連鎖 → 章への配分、という今の流れは3章のときだけ動く。3章以外は古い流れに入り、キャスト計画も連鎖も無い（`script_continuation.cast_plan` の冒頭、`outline` の `count == 3` 分岐）。
- 3章を前提にしている箇所:
  - `script_plot.py`: 連鎖の `events` の説明「3章に収まる」、`ChapterAllocation`／`StepChapterAllocation` の `chapters` が `min_length=3, max_length=3`、連鎖と配分の指示文（「全3章の分量」「3章の各区間で」「全3章へ配分」）。
  - `script_continuation.py`: `_verify_chapters`（3章のプロットにキャスト計画を求める）、`outline` の配分（出来事が3つなら配分をコードで確定、「3章の値を狭義昇順に」）。キャスト計画の指示は章数で「全3章では」を置き換え済み。
  - 章の場面計画は「全N章の第n章」と書くので、章数に追従する。
- 1章あたりの長さの目安は `script_cast.ScriptOptions`（約10分、本文4,000字、台詞2,000字）。章の場面計画が `length_weight` でこれを場面に配分する。

## コンテキストの増え方（分かっていること）

- 章の場面計画の入力は `script_context.fit_context` が組み立てる。収まらないときは、作例を外す → 先の章の予定を短くする → 古い章の原文を履歴メモに置き換える → 直前の章の原文を前から削る（最後の場面は残す）の順。設定・今後のプロット・作業依頼・システム指示は削らない。
- `docs/experiments/script-plan-context-overflow-20261012.md`: 16kのひだまり第3章で、削れない部分だけで上限を超えた。履歴メモは2章分で約1,200トークン（1章あたり約600）。
- 章が増えると履歴メモが1章ごとに増え、先の章の予定は減る。5章なら第3章より約1,200トークン増える見込み（推測、未測定）。16kでは重い作品が3章でも溢れているので厳しい。32kは数字の上では余裕がある。
- 章が増えるとサブも増えやすく、設定の部分も膨らむ（人数と章数の効果は掛け算になる）。
- 測る道具: `scripts/story/check_script_context.py`（保存済みの台本に対し、トークナイザーだけで依頼の大きさを測る）。

## 未確認のこと

- 4章以上での整合性。履歴メモは要約なので古い章の細部ほど落ちる。伏線や物・場所の受け渡しで崩れやすいと予想しているが、推測。
- 生成時間は章数にほぼ比例すると見ている。レビュー（STEP4のプロット確認、各章を読む時間）も章数で増える。
- 章数を増やしても、連鎖の出来事が同じ少なさなら薄い章が増えるだけ。LLMに章数を任せるなら、連鎖の出来事の量から章数を決める形になり、人数が多いほど長くなる。

## 実験の足場

- 台本だけの実験は `scripts/story/check_text.py`（承認スナップショットを `--input` に取る。章数はスナップショットの `world.result.chapterCount`）。キャストを差し替えるなら `scripts/story/check_text_with_cast.py`。どちらも製品のコードを変えない。
- 4章以上を新しい流れで試すには、先に `script_plot.py` の3章固定（配分の形式と指示文）と `script_continuation.py` の `count == 3` 分岐を、章数に合わせる変更が要る。実験用のオプション（`ScriptOptions` に、未設定なら保存形から消える項目）として入れれば、既存の作品は変わらない。
- 前の実験の出力は `outputs/cast-size-20261017/`。読み物の形にした例が `e2e-scripts.html`。
- 見ると良さそうなもの（提案。ユーザーと相談して決める）: 章ごとの場面計画の入力トークン、後の章での食い違い、3章と比べた生成時間の比、手順を持たないサブの有無。

## 作業上の注意

- テスト: `.venv/Scripts/python -m pytest tests/unit --deselect tests/unit/test_audio_files.py` と `tests/integration` を別々に。`test_audio_files.py` は `.venv` に numpy が無いので動かない（今回の変更と無関係）。`test_image_edit_cg_preview.py` のサーバーのテストは、全体実行でまれに落ちる（単独なら通る）。
- Web: `apps/web/node_modules/.bin/tsc --noEmit -p apps/web` と `node --test tests/*.test.mjs`。`npx eslint` は入っておらず止まるので使わない。
- `player.js`・`player.css`・`LiveWizardApp.tsx`・`wizard.css` は作業コピーが CRLF。Bash のヒアドキュメントで書く Python はバックスラッシュが消えるので、そういうスクリプトは Write で書く。
- 実データで確かめるときは、本物のコーディネーターを起動せず、データベースのコピーを使う。ユーザーが動かしているポート8000のコーディネーターには触らない。モデルを使う確認は `services.worker.generation.processes.gpu_lock` を取り、`select_config` と `RoutedLLM` で製品と同じモデル設定にする。
- ユーザーへの説明・途中経過・wrap_up はすべて日本語。wrap_up は recap だけにし、質問やボタンは使わない。質問は本文に書く。設計を相談している間は、実装を提案して終わらない。
