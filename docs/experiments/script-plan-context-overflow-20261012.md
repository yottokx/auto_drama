# 第3章の場面計画がコンテキストを超えた原因の分析（2026-10-12）

「ひだまり1年1組」の第3章で、台本生成が容量不足で停止した。保存済みの資料を集計して原因を調べた記録。新規推論・アプリコード変更・設定変更は行っていない。トークン数の最適化は未着手で、対処は後日検討する。

## 何が起きたか

- 作品: ひだまり1年1組（project `88d1925bb2d749b58503ec478a0fea92`）
- ジョブ: `m3_narrative` `419667c1a97143d298c8531404dd53cf`、第3章。3回試行して3回とも同じ理由で失敗
- 工程: 章ごとの場面計画（`script-plan`）
- モデル: `gemma-4-31B-it-UD-Q4_K_XL`、reasoning none、コンテキスト 16,384

```
script-plan: 入力10148 + 回答枠6144 + 余裕512 tokensがコンテキスト16384 tokensを超えます。
```

入力の上限は 16,384 − 6,144 − 512 = **9,728 トークン**。過去の台本を限界まで圧縮しても入力が 10,148 トークンになり、420 超えた。

鑑賞画面・録画ツールの変更とは無関係。エラーは台本生成用の入力を組み立てる `services/worker/generation/script_context.py` の `fit_context` が出している。

## 入力の構造

`fit_context` は、収まらないときに次の順で圧縮する。

1. 作例を外す
2. 先の章の予定を「目的と到達状態」だけにする
3. 古い章の原文を、保存済みの履歴メモに置き換える
4. 直前の章の原文を、場面の境界で前から削る。ただし**最後の場面は丸ごと残す**

設定・今後のプロット・作業依頼・システム指示は削らない。今回はこの圧縮をすべて適用した状態で超えた。

| | この作品 | 他作品の中央値 | 他作品の最大 |
| --- | ---: | ---: | ---: |
| 削れない部分の合計 | 8,243 | 5,608 | 7,831 |
| 直前の章の最後の場面 | 1,887 | — | — |
| 合計（上限 9,728） | 10,130 | — | — |

削れない部分だけで、過去の他作品の最大を超えている。残りは 1,485 トークンで、1,887 トークンの最後の場面が入らない。

比較対象は、同じ 16,384 設定で第3章の場面計画まで進んだ他作品25件（保存済みの `requests/plan-003-1.json`）。他作品は圧縮の途中で収まっているため、「削れない部分」には、その時点で入力に含まれていた履歴メモを含む。

## 原因

1つの異常ではなく、次の組み合わせで全項目が同時に上限近くまで膨らんだ。

- **メイン3人**: 関係が3組になり、人物の定義も増える
- **別の姿（衣装）あり**: 設定に衣装の定義、システム指示に扱いの指示、作業依頼に前章終了時点の姿が加わる
- **サブキャラの出番を計画済み**: 人物の定義と、予定しているつながりが増える
- **直前の章の最後の場面が長い**: 2,946 文字・1,887 トークン。丸ごと残す決まりなので削れない

衣装を持つ他の4件は、削れない部分が 5,345〜5,741 トークンに収まっている。それらの作品のメイン人数やサブキャラの計画までは照合していない。

## 長い人物ID

後から追加した人物のIDは `character-cef9b8d4-0077-443b-a739-b782ddffebf0` の形式で、1回書くたびに 33〜35 トークンかかる。`character-1` は 3 トークン。

- この入力に長いIDは47回現れ、合計 1,452 トークン。入力全体の約14%
- 現れる場所: 設定に14回、今後のプロットに10回、履歴メモ・台本の話者名・作業依頼に23回
- 同じ入力を短いIDに置き換えて数えると **8,678 トークン**。上限まで 1,050 の余裕で収まる

長いIDは他作品でも使われている（25件中17件、1要求あたり17〜59回）。この作品だけの問題ではないが、取り除ける負担としては最大。衣装・関係・話者名などIDを書く場所が増えるほど効く。

## 対処の選択肢（未着手）

| 案 | 効果 | 備考 |
| --- | --- | --- |
| LLMに渡すときだけ人物IDを短い別名に置き換える | 約 −1,450 | 全作品に効く。入力と応答の両方で対応づけが必要 |
| このモデルのコンテキストを広げる | 収まる | 2026-10-05 に 32,768 で動かした記録あり。速度とメモリに影響 |
| 衣装の記述を、その章で使う分だけ渡す | 数百 | 章で使わない姿の定義を省く |

同じ長いIDは場面本文・注釈など他の工程の入力にも入るので、IDの置き換えは場面計画以外にも効く見込み。ただし他の工程では計測していない。

## 調べ方

- 失敗したジョブは収まる入力を作れなかったため、要求が保存されていない。`job-request.json` と `script/draft-state.json` から、`ScriptRun.setting`・`material`・`chapter_plan` と `fit_context` をそのまま使って入力を再構成した。モデルの実行は差し替え、常に「収まらない」を返させて最小の入力を取り出した。何も書き込んでいない
- トークン数は、`llama-tokenize.exe` と同じ GGUF で項目ごとに数えた
- 再構成した合計は 10,130 トークン、サーバーの計測は 10,148。成功した他作品の要求でも 8,768 対 8,786 で、差はチャット形式の定型部分
- DB は読み取り専用で参照した
