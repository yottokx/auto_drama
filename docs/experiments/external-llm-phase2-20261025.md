# 外部LLMで作品を通しで生成（Phase 2、2026-10-25）

`docs/external-llm-api-plan.md` のPhase 2。製品と同じ流れで、GPT-6 Luna と Claude Haiku 5.5 に作品を通しで書かせた。

## 条件

- スクリプト: `scripts/story/check_text_long.py --product --chapters 3 --context-size 16384 --cast-limit 4`（16kの段の製品の上限。演出の工程も含む）。
- モデル: `openai/gpt-6-luna`、`anthropic/claude-haiku-5-5`。推論なし。温度0.65・top_p 0.95 は GPT-6 Luna にだけ送られる（Anthropic は受け付けない）。
- 入力: 鉄と血 `outputs/cast-size-20261017/inputs/tetsu-qat-product.json`、ひだまり `outputs/long-form-20261020/inputs/hidamari.json`（`long-form-16k-20261021.md` と同じ）。シード1。失敗したものはシード2で作り直した。
- 出力: `outputs/external-llm-20261025/`。
- 費用: 約$0.35（生成$0.32、動作確認と原因調べの呼び出し約$0.03）。料金は両モデルとも入力$0.10・出力$0.50（100万トークンあたり）で計算。

## 実装の修正（この実験の途中で入れた）

最初の実行で、両作品の GPT-6 Luna がキャスト計画で2回ずつ失敗した。サブキャラの上限（16k・メイン3人で1人）と代表台詞の数（3つ）は指示文に書かれておらず、スキーマの `maxItems` / `minItems` だけで守らせていた。Gemma では grammar が黙って止めていた制約にあたる。

- 制約を外して送ると、両モデルとも自然にはサブキャラを4〜5人、代表台詞を2つずつ書いた。Anthropic は `maxItems` と2以上の `minItems` を受け付けないので、このままでは必ず検証で落ちる。
- OpenAI の strict は制約を守らせるが、モデルは知らずに書き進め、止められたところで回答が崩れた（同じ依頼で3回中2回。代表台詞の配列に `"id: c5"` のような要素が入り、日常の接点が空になった）。

外部モデルへの構造化出力の依頼の末尾に、スキーマの件数と数値の範囲をスキーマから自動で書き足すようにした（`llm_providers.schema_limits`、コミット `7df8fe7`）。同じキャスト計画を両モデル・2作品で2回ずつ送り直し、8回とも制約の違反なく通った。Gemma の依頼は変えていない。

### 章の長さ

| 実行 | 本文の字数 | 地の文の比率 | 場面 |
|---|---|---|---|
| GPT-6 Luna・ひだまり | 2,632 / 3,845 / 5,854 | 38% / 30% / 34% | 1 / 3 / 6 |
| GPT-6 Luna・鉄と血（シード2） | 3,135 / 3,575 / 5,158 | 32% / 48% / 39% | 3 / 5 / 5 |
| Haiku 5.5・鉄と血 | 3,296 / 1,688 / 4,161 | 39% / 40% / 41% | 3 / 1 / 3 |
| Gemma・ひだまり（10/21） | 3,997 / 4,860 / 4,735 | 68% / 46% / 66% | 5 / 4 / 3 |
| Gemma・鉄と血（10/21） | 4,437 / 3,683 / 5,354 | 46% / 49% / 71% | 3 / 3 / 5 |

Gemma の行は条件が違う（演出の工程なし、10/22以降の製品の変更なし、鉄と血はキャラ上限5）。比べられるのはおおよその傾向だけ。

- 外部モデルの章は Gemma より短く、地の文が少ない（30〜48%、Gemma は46〜71%）。
- 章の長さのばらつきが大きい。GPT-6 Luna・ひだまりは第1章が2,632字・場面1つで、第3章の半分以下。Haiku・鉄と血の第2章は1,688字・場面1つ。

### 失敗の内容

- **GPT-6 Luna・鉄と血（シード1）**: 第1章の演出（`staging`）で、JSONを最後まで書いた後に止まらず、`</|assistant|>` のような終わりの印を自分で書いてから同じJSONを繰り返し、出力上限8,192トークンに達した。この実行の演出の依頼14回のうち1回。他の実行の演出では起きていない。
- **Haiku 5.5・ひだまり（シード1・2）**: 場面計画で「当章の `outfit_appearances` に割り当てられた姿は、当章のいずれかの場面で必ず登場させます」を守らず、割り当てられた私服（`look1`）を、どの場面の `outfits` にも入れなかった。4回の試行すべて同じ。スキーマでは強制しておらず、検証だけで確かめている決まり。ひだまりはメイン3人に私服がある作品で、衣装違いのない鉄と血は完成した。

### 読んだ印象（各実行の一部の章だけ）

- GPT-6 Luna・ひだまり: 会話が自然で、日常のゆっくりした進み方もよく書けている。
- GPT-6 Luna・鉄と血: 筋は通っているが、兵の配置の手順（交代、矢を一束ずつ運ぶ、車輪と牽引部を狙う）を何度も繰り返す。
- Haiku 5.5・鉄と血の第2章: 場面は1つだけだが、配置の判断をめぐる交渉として筋が通り、中身がある。

## 分かったこと

- 製品の流れは、両モデルとも最後まで通る（構造化出力・本文の形式・台詞の分離・演出）。本文の形式（`話者ID: 台詞`）の崩れは、どの実行でも起きなかった。
- 指示文に書かず、スキーマや grammar の制約で守らせていた決まりは、外部モデルでは指示文で伝える必要がある（今回、件数と数値の範囲は対処した）。
- 費用は3章の作品1つで$0.05〜0.10（見積もりの約$0.2より少ない）。依頼の数は Gemma の2〜3倍だった（演出の工程を含むため）。

## 残っていること

- 同じ条件（今の製品の流れ、演出あり、キャラ上限4）の Gemma の実行がなく、質の比較が大まかにしかできない。
- Haiku 5.5 は、衣装違いの割り当てがある作品の場面計画を通せない。
- GPT-6 Luna の演出の暴走は、製品では、ジョブを失敗にして再試行で引き直すことになる。
- 外部モデルでも台本の実行は GPU のロックを取るので、他の GPU の処理と同時には動かない（今の製品は1ジョブずつなので影響はない）。
