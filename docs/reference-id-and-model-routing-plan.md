# 引用ID対策とモデルの使い分け

日付：2026-09-25  
状態：実装済み（causal protocol implementation 14）。既存作品と過去の実験ログは変更していない。3章通し検証はユーザーの指定により、この実装ターンでは実行しない。

## 1. 決定事項と初期案

| 用途 | モデル | 思考 | コンテキスト |
| --- | --- | --- | --- |
| 本文生成・本文の修復 | Gemma 4 31B | none | 16,384 |
| 意味・整合性の検査 | Qwen3.8 27B | 既定low、mediumを明示指定可能 | 32,768 |

本文をGemma・思考なし・16kで維持し、Qwenの32k使用を許可する点はユーザー指定。新causal経路はQwenのlow・総出力8,192を既定設定に反映した。計画生成・構造抽出・演出付与は引き続きGemmaを使用し、変更する場合は工程別に評価する。比較用legacy経路のモデル割当は変更しない。

Qwenの前回の打ち切りは、入力の16k超過ではなく、思考と最終回答が共有する総出力3,072の上限による。32k化だけでは解消しない。次の評価ではQwenを32kで起動し、総出力上限8,192を初期案とする。これは利用可能な上限で、毎回8,192生成させる指定ではない。

入力tokens＋総出力枠＋余裕が実際のサーバーコンテキストに収まることを、各モデルのtokenizerとtemplateで確認する。low／mediumは思考量への指示であり、最終回答枠の予約ではない。思考部分の上限と回答枠を別に確保する機能も設計対象とし、固定ランタイムでの打ち切り・回答への移行を確認してから使う。xhighを自動選択する経路は設けない。判定が不合格という理由だけでeffortを上げ、合格まで再試行する方式にはしない。

## 2. 引用IDで失敗する原因

変更前の引用DTOは、過去引用にも現在引用にも `utterance_id` という出力欄を使っていた。しかし過去は `q3` 等の短縮ID、現在は `s2-u25` 等の元発話IDを期待していた。現在の[既知情報比較](../services/worker/generation/causal_fact_comparison.py)は以下の単一source_id方式を使用する。

さらに[過去の原文資料](../services/worker/generation/causal_context.py)には、同じ原文について `id: q3` と `utterance_id: s1-u3` の両方があり、知識の `acquired_at` にも元発話IDが現れる。入力にあるutterance_idを同名の出力欄へコピーすると拒否される構造になっている。GemmaとQwenの保存済み実験でこの失敗が反復しており、指示の強調や思考量だけに解決を任せない。

内部の[SourceRef](../packages/contracts/story_workflow.py)は、作品・章・場面・本文版・元発話・原文位置・本文hashを既に持つ。[原文解決処理](../packages/narrative/story_ledger.py)も存在する。まずこの内部参照を維持し、LLMへ見せる参照形式を整理する。

## 3. 推奨案：提示IDを統一し、完全な原文参照はコードで解決する

### 3.1 一つの問い合わせで使うIDを一種類にする

検査リクエストを作る直前に、提示する全原文の対応表をコードで作る。過去と現在を通して重複しない `src001` 等のIDを採番し、入力・出力とも欄名を `source_id` に統一する。

LLMへは別名のq ID・元発話ID・本文hashを重ねて見せない。章番号、話者、前後関係、作中時刻、誰がいつ知ったかは判断に必要なので残す。取得時点が元発話IDなら、同じsource_idまたは明示的な時点表現に変換し、回想が語る過去と、人物が情報を得た時点を区別する。

```json
{
  "source_id": "src001",
  "phase": "earlier",
  "chapter": 1,
  "speaker": "葵",
  "text": "……この三枚、やっぱり時期が特定できない。"
}
```

モデルからは、同じIDと短い逐語引用を受け取る。

```json
{
  "source_id": "src001",
  "quote": "この三枚、やっぱり時期が特定できない。"
}
```

この対応表は当該問い合わせの資料snapshotにだけ有効とし、内部には `source_id → 完全なSourceRef` を保存する。同じ `s1-u3` や同じ台詞でも、章・版・位置が異なれば別参照にする。本文hashだけで別の出現箇所を統合しない。

共有のContextPacketや保存済み台帳を一度に変更する必要はない。まず検査への入出力変換層を設け、内部のq IDと元発話IDはそこで一つのsource_idへ変換する。既存の取得・直前場面接続処理は内部参照を使い続けられる。

### 3.2 IDは候補から選択させる

JSON schemaのID欄は自由な文字列ではなく、提示した候補のenumにする。過去・現在の役割と、事実ごとの引用可能な集合をコード側でも必ず検証する。小さいbatchでは事実ごとに候補を限定したschemaも検証するが、ランタイムが未対応のschema機能に依存しない。

候補にあるからといって主張を支持しているとは限らない。該当根拠がない・判断できない場合に、無理に一つ選ばず `not_referred_to` や `insufficient_evidence` を返せる出力契約にする。候補一覧やschemaが大きくなる場合は意味の論点単位で分割し、全事実の検査範囲を集約する。

### 3.3 原文との照合を維持する

コード側では、選択IDが提示済みか、当該事実・過去/現在の役割で許可されているか、作品・章・版・原文hashが一致するかを確認する。短いquoteも指定した原文内の完全一致を要求する。保存・表示する正式な原文とSourceRefは対応表から取得し、モデルの転記を原文そのものとして扱わない。

当初はquoteを残す。どの節を根拠にしたか確認でき、否定・仮定・依頼をどのように読んだか追えるためである。出力tokensの削減を優先する段階では、コードで短い原文区間を用意してIDだけを選ばせる方式を比較する。長い発話のIDが実在するだけで、その発話が主張全体を支持したとは判断しない。

引用のために元のSourceRefの範囲を勝手に変更しない。quoteからさらに狭い文字範囲を作る必要がある場合は一意な一致を求め、同じ短句の最初の出現位置を自動採用しない。日本語の文字offsetをLLMに計算させない。

## 4. 採用しない方法と移行時の扱い

| 方法 | 判断 |
| --- | --- |
| 「q IDを使え」という指示をさらに強くする | 補助にはなるが、同名欄と二種類のIDの競合が残る |
| 元発話IDなら何でも受け付ける | 章や版を跨ぐ重複で別原文を指すため採用しない |
| quoteだけを全作品から検索してIDを補完する | 同文反復や別版を区別できず、提示していない原文も混入するため採用しない |
| 単一source_id＋候補制約＋厳密な原文照合 | 初期の実装案。IDの転記と意味判断を分けられる |

新規の検査経路では旧IDを黙って補正しない。既存の失敗ログは原本のまま残す。移行上どうしても互換解決が必要なら、当該事実・役割で許可された提示済み候補の中で、完全なSourceRefが一意かつquote/hashが一致する場合だけに限定し、解決前後を記録する。意味判定の再検証を省略して過去の失敗を成功へ書き換えない。

修復時には原文・比較対象・対応表を固定し、返された誤値、期待する欄名、許可候補を具体的に示す。対応表を作り直す場合は新しいsnapshotとして全参照を検証する。元本文の再生成をIDの形式修復へ巻き込まない。

cacheには、解決済みリクエスト全体のhash、モデル重み・template・ランタイムの識別、実コンテキスト、effort、出力予算、seed、prompt/schema/検証器の版、資料snapshot全体のhashを含める。temperature/top_p等の設定追加もリクエスト全体として識別し、資料snapshotには本文・対応表・事実別の許可集合・過去/現在の役割・記憶と本文の版を含める。旧方式の検査cacheを新方式の成功として流用せず、cache再利用時も原文参照と検査範囲を照合する。

## 5. モデル切り替えの扱い

目的別profileから実モデル・コンテキスト・effortを解決し、実モデルの取得/解放は別の管理層へ分離する。現在のLocalLLMは単一モデル前提なので、同じインスタンスのprofileだけを変えてモデルが切り替わった扱いにはしない。Qwenの32k設定をGemmaの本文リクエストへ引き継がない。

最初は依存順を守り、Gemmaで場面の本文を生成し、Qwenの検査を完了してから次の場面へ進む。本文修復はGemma、再検査はQwenに戻す。抽出工程をどちらに割り当てるかは別途評価し、未検証の結果を次場面の採用済み状態へ渡さない。

将来の切り替え削減は、同じモデルで実行可能な検査を続けて処理することと、プロセスの再利用から始める。独立した検査は別リクエストのまま続けられるため、切り替えを減らすために一つの総評へまとめる必要はない。次の本文が直前の検査結果に依存する箇所を跨いで、全章の本文を先に生成する順序へ戻さない。

ロード回数・ロード/解放秒・切り替え待ち・生成秒・修復回数を記録し、計測してから待機中の再利用や実行可能な仕事の並べ替えを追加する。二モデルの同時常駐はVRAM実測後の選択肢とし、今回の前提にはしない。作品ごとの入力・履歴・キャンセル・cacheはプロセスの再利用と分離する。

## 6. 実装・検証する順序

1. 検査の入出力を単一source_idへ変換し、対応表・役割・事実ごとの候補・原文一致の検証を実装する。まず既知情報比較を対象とし、他の検査は同じ考え方で順次統一する。
2. 章を跨いだ同一発話ID、同文反復、本文改訂、別事実の候補、未提示ID、対応表の入れ替え、引用捏造、検査漏れ、古いcacheを拒否する機械的な検証を行う。
3. 保存済みr8本文を固定し、新形式だけを変えた別実験を行う。元ログは不変のまま、ID成功率と意味判定を別々に比較する。
4. 本文Gemma none/16k、検査Qwen/32kを実際に分離する。Qwenの出力枠を拡大してlow／mediumの完了率・意味判定・時間を比較し、出力枠の変更とID形式の効果を混同しない。
5. 過去の矛盾例とその修正版、別題材でも確認してから3章通し生成へ戻る。処理完了と本文の通読評価を両方行い、モデル切り替えの最適化はその計測結果で優先順位を付ける。

参照：[ストーリー再設計](story-workflow-redesign.md)、[実験記録](experiments/story-workflow-poc.md)。

## 7. 実装範囲

既知情報比較に単一source_id、候補enum、逐語引用と完全SourceRefの照合を適用した。他の検査DTOの全面移行、章を跨いだモデル常駐、実行順の並べ替え、思考と最終回答の別枠予約は今後の評価対象とする。

`RoutedLLM` は既存GPUロック内で一つのサーバーを所有する。profile選択やcache再利用はモデルを起動しない。新規推論が必要なときだけロードし、同じモデルを連続して使う間は再利用する。別モデルへ切り替える際は旧プロセスの解放完了後にロードする。リクエスト番号・seed区間・使用量・traceは両モデルで一つの系列を保つ。

job保存・実験再開・stage/request cacheは両モデルの設定内容を識別に含める。Qwenのtemplate hashとllama.cppのbuildを起動時にも照合する。設定を変更した場合は新しい実験ディレクトリを使用する。モデル重みのhashは設定に記録した検証値であり、17GB以上のファイルを各リクエストで再hashする方式ではない。
