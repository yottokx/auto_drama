# イベントCGの利用と検証

Qwen-Image-2.1によるイベントCGは任意機能。通常はこれまでどおりAnimaの背景・立ち絵で制作する。構成承認前に基本CGの上限を正の数へ変更すると、本文確定後にLLMが表示区間と描写を選び、採用済み立ち絵を参照してCGを生成する。

## 有効にする

1. [Qwen画像編集テストの準備手順](qwen-image-edit.md#準備)で専用Diffusers環境とモデルを準備する。既に実験で導入済みなら共用できる。
2. 更新後のCoordinatorと通常のWorkerを起動する。稼働中の旧プロセスには新API・新ジョブ種別がないため、更新後の起動が必要。
3. 「設定」→「画像」で実行環境の準備状態を確認する。既定はBF16・CPUオフロード有効・KVキャッシュ有効・40ステップ。出力は960×640、量子化は未対応。
4. 作品のSTEP4「構成確認」で「イベントCG」の基本CG上限と、CG1件あたりの追加差分上限を保存してから構成を承認する。

基本CG上限は制作版の全章を合わせた件数。たとえば基本3件・追加差分2枚なら、最大9枚。上限を使い切るようには指示しない。両方の既定値は0で、基本CGが0なら作品制作にCG用LLM・モデル確認・画像ジョブを追加しない。Worker起動時の任意機能一覧は軽量なファイル検査だけで判定し、モデルはロードしない。

基本CG上限が正のときは、Qwen対応Workerの準備完了が構成承認の条件になる。設定保存だけでモデルをダウンロードしたり、既存作品へCGを追加したりはしない。N・Dと実行設定は制作版開始時に固定され、後から共通設定を変えても進行中の制作へ遡及しない。

## 制作と再生

構成承認後、第1章の本文生成より先に、LLMが承認済み全体構成から全章のCG枠を一度だけ配分する。正常な配分では章別枠の合計を作品全体の上限と一致させ、提示されていない将来の章へ温存しない。これは利用可能枠の配分であり、生成枚数の使い切りは強制しない。配分が確定するまで本文ジョブは開始しない。各章の枠は配分完了時点で画面に表示し、枠のある章では本文・演出注釈の確定後に具体的なCG区間と画像枚数を選ぶ。区間は同じ場面内の台詞IDで指定し、章またぎや重複は禁止。未使用の章枠は自動で他章へ繰り越さない。

工程一覧はCG有効時に配分・選定・生成の予定を最初から表示し、画像枚数は選定前なら「未確定」、一部の章だけ確定済みなら「現時点」として表示する。配分前に中断していた制作版は、再開時に配分を先に行ってから保存済みの本文生成を続ける。承認済み全体構成を持たない旧形式の制作版のみ、最初の本文から従来の全体構成を取得する。

台本はLLMへ文脈として渡し、画像モデルには英語の視覚的指示だけを送る。人物ごとの位置・動作・表情・視線は既存キャラIDへ結び付け、参照画像番号との対応をコードで構築する。基本CGは人物立ち絵を参照し、各差分は同じ基本CGと人物立ち絵を参照する。前の差分を次の差分の元にしない。

制作画面ではCG配分・選定・基本画像・差分の進捗、生成数、省略数と理由を確認できる。計画の指示作成失敗と画像生成失敗は分けて数える。一部のCG指示が失敗しても、有効な残りのCGを制作する。

CG表示中は背景・立ち絵を隠し、台詞・音声・BGMを通常どおり進める。終了後は、その時点の背景・人物配置へ復帰する。CG途中の保存・再開、スキップ、章切替、ZIP書き出しに対応する。画像の読み込みに失敗した場合は通常の背景・立ち絵へ戻す。

計画や画像の生成に失敗した場合は理由を残して対象CGを省略する。基本CGの省略では子差分も省略し、差分だけの省略では直前の正常な画像を使い続ける。ユーザー中断・通信障害・lease失効は確定した省略とは区別し、既存の停止・再送経路で扱う。公開済みの省略CGを後から自動生成して差し替える機能はない。

通常の背景・立ち絵も作成するため、CGを有効にしても通常素材の生成時間は削減されない。完成後調整による立ち絵・BGM変更で再出版しても採用済みCGは保持し、CG自体は作り直さない。

## 保存と実行

- `m3_event_cg_budget` は作品全体の章配分、`m3_event_cg_plan` は章内の区間と指示、`m3_event_cg` は画像1枚を担当する。
- 原本画像と不透明な表示画像を別artifactへ保存する。ZIPへは表示画像を `data/cgimage/` に含める。
- 計画の元本文・承認構成のhash、参照素材IDとhash、CG/差分ID、Seed、モデルとruntimeの版、実行条件・時間・メモリを記録する。
- 採用済み画像は再開時に再利用する。同じ依頼の完了通知を再送しても画像・上限を二重計上しない。
- GPUロックは親Workerが所有し、Qwenの子プロセスはロックを取り直さない。Anima・LLM・TTS・BGMと切り替えて使用する。同じCGの連続画像では短時間モデルを再利用し、他工程・他CG・待機上限・取消・失敗で解放する。

画像設定のWorker一覧は直近90秒以内に接続したWorkerだけを表示し、終了済みの登録履歴は除く。同じ名前のWorkerでも実際に別プロセスが接続中なら別件として表示する。Worker起動時は作業フォルダーをOSの排他ロックで保護し、同じフォルダーの多重起動を登録前に止める。別のWorkerを意図的に使う場合は `-WorkDir` で別の作業フォルダーを指定する。ロック追加前から稼働していたWorkerでは再起動後に有効になる。

## 実生成の確認（2026-10-04）

RTX 5090・32GB VRAM、BF16、CPUオフロードとKVキャッシュ有効、40ステップ、960×640、Seed 0。既存実験のリナ・アイリスの本文と参照画像を、新しいWorkerの入口から再生した。実作品のDB・公開版は変更していない。

| --- | ---: | ---: | ---: | ---: |
| 2人の基本CG | 100.6秒 | 41.3秒 | 19.57 / 21.64 GiB | 32.45 GiB |
| 基本CGから笑顔差分 | 32.8秒 | 31.6秒 | 22.08 / 24.04 GiB | 38.29 GiB |
| 同じ基本CGから驚き差分 | 29.3秒 | 28.1秒 | 22.09 / 24.26 GiB | 42.66 GiB |
| 1人の基本CG | 72.6秒 | 35.8秒 | 19.10 / 20.63 GiB | 32.39 GiB |

最初のモデル検証22.2秒・ロード29.3秒。差分2枚ではどちらも再利用し、追加ロードは0秒。章配分は10.5秒、章内選定と指示は14.6秒。この表の差分2枚と1人CGはbackend検証用の明示的な画像指示を使い、LLMの枚数・切替判断とは分けた。

GPU値はPyTorchの割当・予約、RAMはWindowsの当該子プロセスのPeakWorkingSetSize。OS・他プロセス・ページファイルを含む総必要容量ではなく、最低動作要件を示さない。同じ子プロセスを使う行のRAM値はプロセス開始からの累積ピーク。参照枚数で負荷は増える。

目視では基本CGの髪・目・制服の特徴と2人の区別を確認でき、台本を文字で埋めた画像にはならなかった。ただし手動差分では色味と線が強く変わり、「驚き」も弱かった。構図・同一人物の特徴が残ることと、表情だけを狙って変えられる品質は区別する。少数例の成功を全キャラ・全場面での一貫性保証にはしない。

### 構造化した人物指示の再確認

最初の実LLM出力では、差分用の参照表が正しくても自由文中でリナとアイリスの画像番号が反転した。このため自由文による番号割当を廃止し、`character_id`をキーにした描写からコードで参照番号を組み立てる方式へ変更した。人物間の視線対象もIDで指定する。未知・不足IDやLLMによる番号指定は修正対象とし、最大1回修復後も不適合なら理由付きで省略する。

修正後はLLMが選んだ基本CGと差分1枚を、そのまま新しいWorker経路で生成・検証した。LLMは章内選定と指示作成に31.7秒、基本CGは98.0秒（推論40.9秒）、差分は31.7秒（推論30.3秒）。差分の参照は画像1=基本CG、画像2=リナ、画像3=アイリスを保持した。アイリスの口と眉の変化を確認できたが、やはり色味と線も強く変わった。追加差分上限の既定値0は維持する。

差分時のGPU最大割当22.19GiB・予約24.12GiB、子プロセスRAMピーク39.98GiB。完了後はLLM・Qwenの子プロセスを終了し、GPU使用量が約1.7GiBへ戻った。記録は `outputs/event-cg-structured-smoke-20261004/`。

## 自動テスト・画面確認

CG専用unit 85件、Coordinator統合13件、実ブラウザーのCG再生3件が通過。フロントエンド全179件・TypeScript検査・本番ビルド、変更したPythonのRuffも通過。設定画面は独立した模擬APIとブラウザーで、準備状態・設定競合・承認条件・390px幅を確認した。画面記録は `outputs/event-cg-ui-review-20261004/`、再生記録は `outputs/event-cg-player-smoke.png`。

全体unitでは3,073件通過・56件skip、既存 `test_audio_files.py` の43失敗と9エラーは軽量環境のNumPy未導入によるもの。最終的な人物指示の修正後は上記CG専用85件を再実行した。全体integrationでは349件通過・11件skip・5件失敗し、そのうち今回のmigration追加に伴うfixture 2件を更新して再実行・通過した。残る `test_adjustment_geometry.py` の2件と `test_m3_portrait_settings.py` の1件は、変更前のscene stage出力に対する旧テスト期待値の不整合で、今回の実装では変更していない。

## 制限

完成後のCG追加・区間編集・タイムラインUI、立ち絵の表情／衣装差分、Qwenによる通常t2iは今回の範囲外。初期版は各人物の標準立ち絵を参照する。3人以上や多数場面の品質、量子化、低VRAM環境は未評価。
