# Qwen Image 2.1 キャラクター画像テスト

プロジェクトルートの `qwen-image-test-gui.bat` をダブルクリックして起動します。Stable Audio実験と同じ独立Windows用Tkinter GUIです。画像生成は専用環境のDiffusers `QwenImage21Pipeline` と公式公開重みを使います。

## 準備

「環境・モデル準備」で「① 専用環境を準備」「② モデルを取得」の順に実行します。Python・PyTorch・Transformers・Diffusersは `services/worker/runtimes/qwen_image_edit/` に分離し、既存のAnima・音声環境と独立しています。モデルだけで約33GBあり、専用環境や生成画像の保存にも空き容量が必要です。ダウンロード途中のモデルは同じ保存先のステージへ置き、検証後に移動します。

このPCのRTX 5090・32GB VRAMでの初期設定はBF16・40ステップ・CPUオフロード有効です。視覚生成部以外にテキスト・画像エンコーダーとVAEもあるため、パラメーター数だけから全体がVRAMへ収まるとは判断しません。最初は立ち絵768×1152、一枚絵1024×576を使います。幅・高さは32px単位で指定します。

環境準備はCLIからも実行できます。

```powershell
.\scripts\setup-qwen-image-edit.ps1
```

モデルは公式リポジトリの確定リビジョンを取得し、全ファイルのSHA256と必須構成を検証した後に公開します。生成はオフラインで、その固定済みモデルだけを読み込みます。既存のモデルや実験結果を上書きしません。Hugging Faceの既存ログインは参照できますが、トークンを設定・生成記録に保存しません。利用条件は[公式モデルページ](https://huggingface.co/Qwen/Qwen-Image-2.1)で確認できます。

## 立ち絵の差分

1. 「立ち絵の差分」でPNG・JPEG・WebPを1枚追加します。
2. 表情・ポーズ・衣装のプリセットを選び、「テンプレートを入れる」を押します。
3. 最終の生成指示を編集し、生成します。例: 笑顔、怒り、腕を組む、手を振る、冬服。
4. 「比較・評価・履歴」で元画像と出力を比較します。透明部分は市松模様で表示します。

参照画像はEXIF方向を反映し、RGBAへ正規化して実験フォルダーへ固定します。元の立ち絵にRGB変換や背景除去を上書きしません。透明背景はモデルへの指示で、生成物のアルファ値を記録します。不透明な出力や全画素が透明な出力には警告を表示します。

生成結果を差分の参照にすると、現在の基準画像をその結果に置き換えて連続編集できます。各出力の親画像・実験・Seedを保存します。一貫性を比較するときは、元の立ち絵から毎回生成する条件と、生成物を続けて編集する条件を区別してください。

## 場面の一枚絵

「場面の一枚絵」で1〜10枚を追加します。参照画像は一覧の上から画像1・画像2…の順番です。人物名を付け、順番を変更できます。例: 「画像1の詩織は左、画像2の陽葵は右。夕方の喫茶店で同じノートを覗き込んでいる」。構図・動作・背景・人物ごとの役割を明示すると比較しやすくなります。

ローカル画像だけで実験でき、作品サーバーは不要です。作品から選ぶ場合はcoordinatorを起動し、作品一覧を更新します。実験専用の読み取りAPI `/api/image-experiments/projects/{id}` が、現在選択した制作版・調整版・凍結履歴の全章を一つのスナップショットとして返します。公開された後続章の脇役も一覧に含まれます。立ち絵と本文は公開版の参照へ固定し、閲覧に伴う制作再開・ジョブ追加・素材差し替えを行いません。

実装前から起動していたcoordinatorには新APIがないため、作品一覧でHTTP 404が出た場合はcoordinatorを起動し直してください。未公開素材はローカル画像から追加できます。

場面と登場人物の立ち絵を選び、「LLMで指示を作成」を押します。LLMが台本・場所・場面の目的を読み、一枚に描く瞬間を選んで、人物の動作・表情・視線・位置、背景・光・カメラの構図を英語の画像生成指示へ変換します。人物は参照画像の番号へ対応させ、元の顔・髪・衣装を参照で保つよう指示します。選択した参照人物のうち、その瞬間に登場しない人物を無理に画面へ入れないようにしています。

「LLMへの追加指示」で、例「リナを左、アイリスを右。操縦桿を握り直す瞬間。腰上の構図」などを指定できます。日本語の「LLMの場面解釈」と最終の英語指示を確認し、必要なら手直しして生成します。台本の本文・台詞・制作上の字数指示を画像モデルへ転載しません。LLMが有効な指示を返さない場合は一度再試行し、失敗を表示して現在の入力を保持します。

既定のLLMは「LLM設定」の `llama_cpp` です。本体で登録済みのGGUFモデルとllama-serverを再利用し、プロンプト作成だけの専用プロセスで読み込みます。本体のGPUロックを共有し、LLMを終了してGPUメモリーを解放した後で画像生成へ進めます。Ollama・OpenAI互換APIも選択できます。画像生成用のDiffusers環境へLLMをインストールする必要はありません。

場面を変えただけで生成指示を上書きしません。LLMの作成中に場面・参照・入力を変えた場合、その古い結果は画面へ適用しません。またLLM作成後に場面や参照順を変えた場合、未編集のLLM指示で生成する前に作り直しを案内します。自由入力だけで使うときは「参照番号を追加（手入力用）」で参照と人物名の対応を付けられます。

## 印象的な一枚（LLM任せ）

イベントCGの構図を改善できるかを試すためのタブです。立ち絵は選びません。作品・章・場面を選んで「LLMで案を作成」を押すと、LLMが場面を読み、互いに異なる案を3つ返します。背景は[構図・差分の実験計画](../experiments/event-cg-composition-variants-plan-20261007.md)にあります。

LLMが決めるのは、描く内容、登場させる人物、カメラと配置、表示する発話の範囲、英語の画像指示です。人物はその場面の登場人物のうち公開版の立ち絵がある人から1〜3人で、全員を描く必要はありません。「二人を横から中距離で並べる」構図は、3案のうち多くても1案に抑えるよう指示しています。

指示の第2版（2026-10-07）では、最初の試行結果を受けて目的を「場面で最も印象的な一瞬」から「会話の間ずっと表示される、その場面の中心のやり取りの絵」に改めました。第1版は、会話と関係の薄い脇の出来事や一瞬の動作を選び、人物と設備の位置関係が崩れ、店内が空っぽに描かれる例がありました。第2版の変更点は次のとおりです。

- 会話を担う人物を描く。候補ごとの発話数を渡し、主な話者を外すのは別の人物の反応が主題のときに限る。
- 保持できる状態を描く。跳ぶ・倒れるなどの一瞬の動作は避ける。
- `display_from`・`display_to` で、その絵を表示する発話の範囲を答えさせる。場面の半分以上を目安とし、まだ起きていない出来事は描かない。一覧の「表示する発話」に出る。
- `layout` で、カメラを決める前に物理的な配置（カウンターや席などの固定物、各人物がどちら側にいるか、カメラの位置）を書かせ、画像指示の先頭に入れる。
- 場所には、そこにあるはずの具体的な物を3つ以上書かせる。「静か」「無機質」は雰囲気であり、空の部屋の指定ではないと明記。
- 引用符で囲んだ語を含む指示は不採用にする。第1版では `'OVERDUE'` が画像に文字として大量に描かれた。
- 3案は同じ瞬間・同じ人物でもよく、カメラと演出を変える。第1版の「互いに異なる案」は脇の出来事を選ぶ原因になった。

第3版（同日）は、光を独立した必須項目 `light` にしただけです。第2版で、深夜の明るいコンビニが真っ暗に描かれた案がありました。その案の指示には光の記述がなく、「midnight」が暗さとして描かれていました。`light` には明るさと光源を1文で書かせ、「夜でも店や乗り物の中は自前の照明で明るい」と明記して、画像指示の先頭付近に入れます。

方針として、読み進める中で気づかない程度の細かな矛盾（手や小道具の持ち主の取り違えなど）は許容し、LLMの裁量を狭める制約は増やしません。一目で分かる事実（場所の種類、明るさ、屋内か屋外か、天候、誰がいるか）だけを場面に合わせるよう求めています。

第4版（同日）は「顔の小物を追記」を追加しました。メガネなど顔まわりの小物は欠けると目につきやすい一方、指示で顔に触れると顔を見せる構図へ寄るおそれがあります。そこで順序を分けています。LLMには承認済みの外見設定（`appearance`）を渡し、選んだ人物ごとに顔・頭の小物を英語の短い語句（`face_items`）で答えさせますが、人物の選択やカメラには使わないよう指示します。画像指示への追記はコードが行い、見え方が正面・横顔の人物にだけ「always has …」の一文を足します。背中や一部だけの人物には足しません。チェックの有無で変わるのはこの一文だけなので、同じ案・同じSeedで比較できます。調べた範囲では、この影響を測った研究や、小物の再現を評価するベンチマークは見当たりませんでした（[ViStoryBench](https://arxiv.org/html/2505.24862v4) は顔や人物の切り出しの類似度で一貫性を測り、小物や顔の見えない構図は扱っていません）。

依頼と画像の記録には `prompt_version` を保存しており、版ごとの結果を区別できます。

次の点はLLMに任せず、コードで決めます。

| 項目 | 内容 |
| --- | --- |
| 候補の人物 | 場面の登場人物と立ち絵を自動で対応させ、A・B…の記号を付けて渡す。立ち絵のない人物は名前だけ伝える |
| 人数の上限 | 参照画像のメモリー使用量を抑えるため3人まで。超えた回答は不採用 |
| 参照番号 | LLMは人物を `<A>` のような記号で書く。選ばれた順に「Reference image N」へ置き換える |
| 外見保持の文 | LLMが申告した見え方（正面・横顔・背中・一部）ごとに切り替える。背中向きの人物には顔の保持を求めない |
| 読み込む立ち絵 | 生成する案で選ばれた人物の分だけを、生成の直前に取得する |

長い場面でも発話を間引かず、1発話あたりの文字数を詰めて全発話をLLMへ渡します。「立ち絵のない人物を人影として許可」を外すと、選んだ人物以外を描かない指示に変わります。「下部のメッセージ枠を避ける」は、重要な顔や動作を画面下4分の1より上に置く一文を追加します。既定の出力サイズは本番と同じ960×640です。

一覧で案を選ぶと、描く瞬間・見どころと最終の画像指示を確認でき、指示は手で直せます。「現在のタブを生成」は選んだ案を、「全ての案を順に生成」は3案を続けて生成します。途中で失敗・停止した場合、残りの案は生成しません。

LLMの依頼と回答は `cg-proposals-…/`、画像は `cg-…/` に保存します。画像側の `request.json` の `context.cg_proposal` に、案の全項目、候補の人物、追加指示、各オプション、指示を手で直したかを記録します。比較画面では結果を選ぶと案のショット・アングル・描く瞬間を表示し、評価項目に「構図の適合」「印象の強さ」を追加しています。

同じ場面を「場面の一枚絵」タブでも生成すると、従来の指示との比較になります。

### ティラノで場面を再生

「比較・評価・履歴」タブで、このタブから生成した結果を選び「ティラノで場面を再生」を押すと、ブラウザーで鑑賞画面が開きます。その案の「表示する発話」の範囲だけがCGに切り替わり、それ以外は公開版と同じ背景・立ち絵・音声・BGMで再生します。開始画面の「つづきから」を押すと、その場面の冒頭から始まります（章の最初の場面は「はじめから」）。読み込み直すたびに場面の冒頭へ戻ります。

本体のプレイヤー・作品サーバー・作品データは変更しません。公開版の台本を作品サーバーの既存の鑑賞用の配信口から読み取り、CGの表示区間を1件足して実験UIの中でコンパイルし直します。差し替えるのは台本・シナリオ・舞台状態・CG画像だけで、音声・画像・ティラノ本体は作品サーバーからそのまま中継します。配信はこのPCの中だけ（127.0.0.1）で、GUIを閉じると終了します。作品サーバーが起動していること、その章が公開済みであることが必要です。

- 同じ区間に採用済みのCGがある場合は、重なるものだけを実験の画像に置き換えます。重ならない採用済みCGはそのまま表示します。
- 「指定した台詞から始める」入口がプレイヤーにないため、実験用のページを開くときに、再開位置として場面の先頭を記録しています。保存先は実験用の配信口ごとに分かれており、本番の鑑賞のセーブには影響しません。
- 一度に差し替えられるのは、選んだ結果の1枚です。
- ボタンの横の「CGの切り替え」で、通常画面とCGの間の効果と時間を選べます。「なし」は現在の本編と同じ即時の切り替え、「クロスフェード」は前の画面が指定の時間で薄れて次の画面が現れ、「暗転」は黒へ落ちてから復帰します（往復で指定時間の2倍）。場面転換用に本編のプレイヤーが持っている効果をCGの切り替えにも当てているだけで、本編の設定（即時）は変えていません。区間内で絵が変わらない台詞では効果は出ません。その台詞に場面転換が設定されている場合は、場面転換の効果がそのまま使われます。

実ブラウザーでの確認は `tests/integration/test_image_edit_cg_preview_browser.py`（`AUTO_DRAMA_CG_SMOKE=1`）にあります。

## 解像度とVRAMの設定（2026-10-09 実測）

「印象的な一枚」タブの既定の出力サイズは1536×1024です。「環境・モデル準備」タブの「生成環境」で、VRAMに関わる3項目を切り替えられます。「VRAMの目安から設定」を選ぶと3項目をまとめて設定します。

| 目安 | 参照解像度 | KV cache（参照の再利用） | VRAMピーク | 推論時間 | 特徴 |
| --- | --- | --- | --- | --- | --- |
| 32GB（標準） | 1024 | あり | 22.8GiB | 約71秒 | 既定 |
| 24GB | 768 | あり | 19.4GiB | 約50秒 | 速い。参照の細部がわずかに粗くなる |
| 24GB | 1024 | なし | 16.6GiB | 約125秒 | 参照の細部を保つ。時間は約2倍 |

条件は3人参照・1536×1024・BF16（量子化なし）・40ステップで、VRAMピークはPyTorchの割り当ての最大値です。このほかにPyTorchが確保して使っていない分とCUDAの管理分で2〜3GiB、デスクトップ表示などの常駐分が乗ります。24GB向けの2つは、PyTorchの使用量を22GiBに制限した状態で完走することを確認しました。24GBの実機では試していません。

VRAMを決めているのは出力サイズではなく、参照画像の枚数と参照解像度です。参照は1枚ごとに参照解像度の2乗相当の画素数へ拡大され、テキストエンコーダーと描画の両方で使われます。出力を960×640から1920×1280に上げても、ピークの増加は1GiB未満でした。参照が2人以下なら、上の表より1〜2GiBずつ軽くなります。

「テキストエンコーダーを層ごとに処理」は既定でオンです。17GBあるテキストエンコーダーを丸ごとGPUに載せず、層を順に載せて処理します。この工程のピークが22.3GiBから6.0GiBに下がり、所要時間は変わらず、生成画像は従来の方式と1バイトも変わりません（同じ条件でファイルのハッシュが一致）。描画本体とVAEは従来どおり1つずつ載せ替えます。描画本体を載せたまま1536×1024の仕上げに入ると、仕上げだけで7〜9GiB使うためピークが30GiBに達しました。

16GB以下は、量子化なしでは収まりません。描画本体だけで14GBあり、参照768・KV cacheなしでもピークは15.8GiBで、PyTorchの使用量を14GiBに制限すると途中でメモリー不足になりました。

### 8ビット版（描画本体をfp8で保持）

「描画本体を8ビット（fp8）で保持」をオンにすると、14GBある描画本体の重みを8ビット浮動小数で持ち、各層を計算する瞬間だけ元の精度へ広げます。専用環境にあるdiffusersの機能だけで動き、パッケージやモデルファイルの追加は不要です。テキストエンコーダーは量子化しません（層ごとの処理でピークが6GiBまで下がっているため）。bitsandbytesの8ビット整数やGGUFのQ8とは別の方式です。

描画本体が小さくなると、最後の仕上げ（画像への変換）が全体のピークになります。1536×1024を一度に変換するのに約9GiB使うためです。「仕上げを分割して処理」は、768pxの区画を128px重ねて変換し、境目をなじませます。8ビット版と組み合わせて使います。

| 目安 | 参照解像度 | KV cache | VRAMピーク | 推論時間 | 上限をかけた完走確認 |
| --- | --- | --- | --- | --- | --- |
| 24GB | 1024 | あり | 16.2GiB | 約63秒 | — |
| 16GB | 768 | あり | 12.8GiB | 約51〜58秒 | 14GiBで完走 |
| 16GB | 1024 | なし | 10.0GiB | 約134秒 | 14GiBで完走 |
| 12GB | 768 | なし | 9.2GiB | 約87秒 | 10GiBで完走 |

いずれも8ビット＋分割ありの値です。分割なしでは、参照1024・再利用ありが16.8GiB、参照768・再利用ありが14.1GiBで、14GiBの上限では途中でメモリー不足になりました。速度は量子化なしと変わりません。

画質は同じ案・同じSeedの1枚で比べただけです。構図と3人の顔・髪・ゴーグルは同じで、口元などの細部が変わりました。分割の境目は縮小表示では見えませんでしたが、等倍での確認はしていません。小物の再現や引きの構図での差、別のSeedでの安定性は未確認です。記録は `vram-fp8-20261009-072745` と `vram-fp8-tile-20261009-073414` にあります。

参照768の画質は、顔が大きい構図の1枚で確認しただけです。3人の顔・髪・ゴーグルは保たれ、512では制服のワッペンや柄が簡略化されました。メガネなどの小物や、顔が小さい引きの構図での差は未確認です。

計測の記録は `outputs/image-edit-tests/` の `hires-memory-20261009-002027`、`vram-phases-20261009-003603`、`vram-layers-20261009-005341` にあります。

## 比較・評価

「Seed 0・1・2で比較」を選ぶと、同じ参照・指示・条件で3枚を順に生成します。全結果を残し、良い1枚だけから品質を判断しないようにします。KVキャッシュや前処理も出力に影響するため、同じSeedの比較ではこれらの設定を揃えます。

元画像と生成画像を並べ、拡大して、全体および参照人物ごとの評価とメモを保存できます。顔・目、髪、体格、衣装、画風、指示への適合、人物の混同、人数・手足を確認します。衣装変更の試験で衣装保持が対象外になる場合はN/Aを使います。生成成功・PNG保存・透明背景の有無は、キャラの一貫性を証明する評価ではありません。

最初の比較は、同じキャラの表情・ポーズ・衣装を別々に変える試験、2〜3人の場面で顔・衣装が混ざらないかの試験、連続編集で元のデザインから離れないかの試験を行います。

## 保存・停止

既定の保存先は `outputs/image-edit-tests/`、GUI設定は `private/image-edit/gui-settings.json` です。

| 保存物 | 内容 |
| --- | --- |
| `request.json` | 画面から確定した指示・設定・人物と場面の出典 |
| `inputs/reference-01.png` など | 実際に参照したRGBA画像の固定コピー |
| `outputs/image-01-seed-….png` | 各Seedの完成画像 |
| `generation.json` | 元画像と正規化画像のハッシュ、参照順、実Seed、モデル版、ライブラリ版、時間、VRAM、アルファ情報 |
| `status.json` / `result.json` | 処理の進捗と結果。中断時の完成済み画像も残す |
| `process.log` | モデル読込・推論・失敗の詳細 |
| `review.json` | 出力別・人物別の評価とメモ |

LLMによる指示作成も `scene-prompt-…/` に依頼・結果・ログを保存します。画像生成の `request.json` の `context.prompt_generation` に、その依頼の出典・場面解釈・モデル・LLM解放の確認を記録します。台本は出典として記録し、画像モデルへ送る `prompt` は変換後の画像指示だけです。

本体のGPUロックを共有して、他のローカル生成と順番に実行します。「停止」は実験自身の処理だけを中止します。バッチの途中で止めた場合、完成済み画像は「中断・一部」の履歴として読み込めます。推論・後片付けを終えてからGPUロックを解放し、生成プロセス終了でモデルを解放します。環境の依存インストール中に閉じる場合は、インストール完了まで待ちます。
